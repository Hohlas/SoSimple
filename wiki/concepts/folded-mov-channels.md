# Folded mov_h Channels

> Свёртка 10 up_X/dn_X каналов в 5 mov_X: убирает 87–90% шумовых нулей, сокращает размерность вдвое.
> Для breach-классификации RF не даёт uplift (Stage 3: −64…−166 bp), но концепт пригоден для других таргетов. `Nero.csv` не менять: `mov_h` вычислять в Python при необходимости.

## Суть

Фрактальные каналы `up_3`…`up_48` и `dn_3`…`dn_48` направленно привязаны к типу фрактала:

- **Пик (dir=1)**: цена не идёт выше пика → `up_X ≈ 0` (86.7% нулей), `dn_X` несёт сигнал
- **Впадина (dir=−1)**: цена не идёт ниже впадины → `dn_X ≈ 0` (89.8% нулей), `up_X` несёт сигнал

Свёртка: `mov_X = up_X` если `dir=−1`, иначе `dn_X`. Результат — 5 каналов вместо 10 с сохранением около 97% ненулевого сигнала в «правильном» направлении.

## Данные (100 фракталов × 44 159 строк train)

| | Пики (dir=1) n=806 393 | Впадины (dir=−1) n=936 698 |
|---|---|---|
| up_12 нули | **86.7%** | 2.4% |
| up_12 mean/median | 0.015 / 0.000 | 0.597 / 0.588 |
| dn_12 нули | 3.1% | **89.8%** |
| dn_12 mean/median | 0.601 / 0.599 | 0.013 / 0.000 |

3.1% нулей в «правильном» направлении — от свежих фракталов (f0–f1), для которых h-баровое окно ещё не истекло.

## Когда применять

- Если up/dn нужны как признаки для направленных таргетов (directional forecast, `edge_h` регрессия, fav_val)
- **НЕ для текущей breach-классификации RF**: Stage 3 показал, что комбинированный профиль `base_plus_path` с `mov_h`, `shift`, `atr_ratio` ухудшает AUC на −64…−166 bp
- НЕ добавлять в ближайший XGBoost/LightGBM проход по `relative_geometry`: этот профиль использует 1011 фич и не включает `mov_h`
- ~11% «чужих» ненулевых значений (оба >0) теряются при свёртке — это может быть важно для разворотных сигналов

## Реализация

Свёртка делается на Python-стороне, без изменения `Nero.csv` или `lib_PIC.mqh`:

```python
mov = np.where(dirs == -1, up_vals, np.where(dirs == 1, dn_vals, 0.0))
```

Такой подход уже используется в `_extract_path()` скрипта `ML/baseline/benchmark_fractal_stop_stage3.py`.

## Nero.csv: оставить без изменений

- 10 исходных up/dn полей в 23-полевом формате `fractal` — source of truth
- Свёртка тривиальна на Python-стороне, переэкспорт MT4 не оправдан
- Переписывание `lib_PIC.mqh`, переэкспорт `Nero.csv` и повторный relabel всех сплитов — на порядок больше работы без практической пользы для текущего этапа
- «Чужие» ненулевые значения (~11%) могут пригодиться для других таргетов

## Текущее решение

1. Оставить `Nero.csv` как есть: 23 поля на фрактал, включая 10 исходных `up_X`/`dn_X`.
2. `mov_h` считать в Python только в тех экспериментах, где он нужен.
3. Не менять MT4-export ради производного признака, который вычисляется одной `numpy`-операцией.
4. Ближайший приоритет — Stage 3.1 / XGBoost на очищенном `relative_geometry`, где `mov_h` не участвует.
