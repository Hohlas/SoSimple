Анализ lib_PIC.mqh — алгоритм и найденные проблемы
Как работает алгоритм (краткое резюме)
PIC() — на каждом баре проверяет, является ли бар [bar+PicPer] локальным экстремумом в окне 2*PicPer+1. Если да — NEW_LEVEL().

NEW_LEVEL() — перебирает весь массив F[]:

Для сонаправленных фракталов: обновляет совпадения, передний фронт
Для противоположных фракталов: обновляет Back, BackVal, Pwr; может установить Strong=1
Записывает новый фрактал в ячейку самого слабого (по Weight = Pwr * FltNum / Distance / (Brk+1))
Вызывает NERO_CSV_CREATE(bar) — запись строки в CSV
NERO_CSV_CREATE() — экспортирует текущий snapshot всех фракталов в CSV

Найденные проблемы
1. Survivorship bias при eviction (принципиальная проблема)
Слабые фракталы вытесняются из массива F[] до того, как накопят большой back. В label_signals.py для вытесненных фракталов берётся последний back перед исчезновением. Результат: систематическое занижение predict для слабых фракталов, что создаёт ложную корреляцию между силой фрактала и величиной predict.

2. Back обновляется только при появлении противоположного фрактала
lib_PIC.mqh:238-244 — Back обновляется только в момент NEW_LEVEL() для противоположных пиков, а не на каждом баре. Если после фрактала-вершины не формируются впадины в течение долгого времени, Back остаётся на старом значении. Это делает Back не монотонным по времени и зависимым от плотности фракталов.

3. Инициализация Back — PicPer баров, а не 1 бар
lib_PIC.mqh:276: F[n].Back = LOWEST(PicPer, bar) — при создании фрактала Back инициализируется как экстремум за PicPer баров ПОСЛЕ фрактала. Это значит, что начальный BackVal может быть уже довольно большим, создавая стартовое смещение.

4. Незащищённая перезапись Rev (Minor)
lib_PIC.mqh:264: F[n].Rev=0 — при создании нового фрактала Rev устанавливается в 0, а затем F[n].Rev=1 только если New > F[hi].P. Но в CSV экспортируется F[f].Rev (float), а Rev это float поле, но устанавливается только 0 или 1. Похоже, изначально Rev задумывался как сила разворота (Pwr предыдущего пика по документации), но по факту это бинарный флаг.

5. Нет ошибок в самом алгоритме поиска фракталов
Код детекции (HIGHEST/LOWEST в окне 2*PicPer+1) корректный. Сортировка по весу и выбор ячейки для замены логически выверены.

Обсуждение Предложения 1: Фиксированный горизонт таргета
Диагноз текущего predict
Текущий predict = -max_back * direction, где max_back — максимальный back от момента формирования до пробития/вытеснения. Три ключевых проблемы:

Переменный горизонт: один фрактал пробивается через 3 бара, другой через 300. Модель не знает горизонт и не может научиться.
Смешение информации: predict объединяет "насколько двинулась цена" и "как долго существовал фрактал" — это confound.
Survivorship bias: вытесненные фракталы систематически получают меньший predict.
Вариант 1 (MFE/MAE) — рекомендую
MFE_N = максимальное благоприятное движение за N баров
MAE_N = максимальное неблагоприятное движение за N баров

Преимущества:

Чистая семантика: два независимых, однозначно определённых числа
Натуральная цель для ML: отношение MFE/MAE ≈ Profit Factor. Если модель научится предсказывать его — это сразу торговый сигнал
Возможность гибких стратегий: модель может учиться предсказывать MFE_24 > 2*MAE_24 (risk/reward > 2:1)
Фиксированный горизонт устраняет все три проблемы выше
Рекомендуемые горизонты: 12, 24, 48 (96 можно добавить, но с осторожностью — на H1 это 4 суток, много шума).

Вариант 2 (B_N) — не рекомендую
Проблемы:

Разрыв в распределении: значение резко переключается с положительного на 0/отрицательное при пробитии. Регрессионные модели плохо работают с такими разрывами.
Смешение двух сигналов: "величина обратного хода" и "факт пробития" — это разные вещи, и запихивать их в одну переменную означает потерю информации.
Меньше гибкости: с MFE/MAE можно конструировать любые производные таргеты (MFE-MAE, MFE/MAE, max(MFE-threshold, 0)), а из B_N — нет.
Где реализовывать MFE/MAE?
Оптимальный подход: в Python, но для этого нужны барные данные.

Обсуждение Предложения 2: Контекст режима рынка
Хорошая идея. Конкретно:

ATR_ratio = Atr.Fast / Atr.Slow — уже доступен в MQL4! Нужно только добавить в CSV экспорт. Отражает "волатильность сейчас vs. средняя" — это и есть режим рынка.

Час / День недели — можно вычислить из fractal_time в Python. Не нужно менять MQL4. Циклическое кодирование (sin/cos) — правильный подход.

Мои дополнительные предложения
1. Нормализация MFE/MAE на ATR (критически важно!)
Абсолютные MFE/MAE бесполезны — движение в 50 пунктов при ATR=20 и при ATR=100 означают совершенно разные вещи. Таргеты должны быть:


mfe_N_norm = MFE_N / ATR_at_fractal_time
mae_N_norm = MAE_N / ATR_at_fractal_time
Это даёт безразмерные величины (в "единицах ATR"), сопоставимые через разные рыночные режимы.

2. Добавить close_at_fractal в экспорт
Сейчас экспортируется price фрактала (экстремум High или Low). Но для вычисления MFE/MAE в Python нужна цена входа. Для трейдера вход происходит не по экстремуму, а по Close бара (или Open следующего). Добавить Close[bar+PicPer] в экспорт фрактала — одна строка в MQL4.

3. Разделить target на два этапа: direction + magnitude
Вместо одного predict (знаковая величина), лучше:

Stage 1 (classification): предсказать direction — Buy/Sell/Neutral
Stage 2 (regression): предсказать magnitude = MFE/ATR для данного direction
Это разрывает confound "направление зашито в знак predict" и позволяет модели фокусироваться на силе сигнала.

4. Добавить spread / "cost of entry" в расчёт
MFE_N нужно уменьшить на спред, а MAE_N — увеличить. Без этого на коротких горизонтах (N=12) MFE будет систематически завышен.
