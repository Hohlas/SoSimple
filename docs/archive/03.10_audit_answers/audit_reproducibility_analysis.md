1. **Изменение кода нормализации** — в разговоре `7d96cdb5` (2026-02-22) отключался StandardScaler. Это могло повлиять на результаты.

3. **Другие гиперпараметры** — февральские запуски не логировались, их параметры неизвестны.
4. **Баг в логировании** — возможно, result JSONs перезаписывались некорректно (race condition или ошибка в `compare_architectures.py`).

### Чего критически не хватает ❌

| Отсутствует | Почему важно |
|-------------|-------------|
| **`seed`** | Без фиксированного seed невозможна точная воспроизводимость |
| **`weight_decay`** | Ключевой гиперпараметр регуляризации, влияет на оверфиттинг |
| **`hidden_size`, `num_layers`** | Архитектурные параметры модели |
| **`seq_len`** | Длина входной последовательности фракталов |
| **`loss_function`, `loss_params`** | HuberLoss delta, FocalLoss gamma |
| **`gradient_clipping`** | max_norm для clip_grad |
| **`scheduler_*`** | Параметры ReduceLROnPlateau |
| **`git commit hash`** | Привязка к конкретной версии кода |
| **`data file hash/version`** | Привязка к конкретной версии данных |
| **`val_loss`** | Для анализа оверфиттинга |
| **`metric_mode`** | Какая метрика использовалась для early stopping |

> [!IMPORTANT]
> Без `seed` и `git commit` даже при идентичных гиперпараметрах результаты **не воспроизводимы**. Это главный пробел.

## 3. Предлагаемые тесты для подтверждения воспроизводимости

### Тест 1: Контролируемый перезапуск (QW-5 из аудита)

```bash
# Фиксируем seed=42, запускаем все 4 модели:
source ~/git/SoSimple/.venv/bin/activate
python -m ML.compare_architectures --task regression
```

**Критерий**: BiLSTM Pearson r ≥ 0.50 на validation.

**Что проверяем**: получаем ли мы высокие результаты (≈0.55) или низкие (≈0.32).

**Что записать**: полные параметры запуска, seed, git commit hash, время, результаты всех 4 моделей.

### Тест 2: Проверка детерминизма (seed stability)

```bash
# Три запуска с одинаковым seed:
for i in 1 2 3; do
  python -m ML.train --model bilstm --task regression --seed 42 --epochs 50
done
```

**Критерий**: разброс Pearson r между запусками < 0.01.

**Что проверяем**: seed действительно обеспечивает воспроизводимость (CUDA non-determinism может давать небольшую вариацию).

### Тест 3: Проверка чувствительности к seed (seed sensitivity)

```bash
# Пять запусков с разными seed:
for seed in 42 123 456 789 1000; do
  python -m ML.train --model bilstm --task regression --seed $seed --epochs 50
done
```

**Критерий**: стандартное отклонение Pearson r < 0.03 между seed-ами.

**Что проверяем**: результат r=0.55 — это стабильный результат или удачный seed? Если один seed даёт 0.55, а другие — 0.32, то модель нестабильна.

### Тест 4: Проверка целостности pipeline данных

```bash
# Хэш входных данных — зафиксировать для воспроизводимости:
md5sum DATA/Nero_train_labeled.csv DATA/Nero_validation_labeled.csv DATA/Nero_test_labeled.csv
```

**Критерий**: хэши совпадают при всех запусках.

**Что проверяем**: данные не менялись между экспериментами.

### Тест 5: A/B между версиями кода

Если Тест 1 покажет r ≈ 0.32, нужно:
1. Проверить `git log` за февраль-март для файлов: `data_loader.py`, `train.py`, `models/*.py`, `normalize.py`
2. Откатиться на февральский коммит и повторить запуск
3. Выяснить, какое конкретное изменение вызвало деградацию

## 4. "Проблема — в данных, не в архитектуре" — разбор

Это ключевой вывод аудита. Вот что он означает конкретно:

### Факты, на которых основан вывод

| Факт | Числа |
|------|-------|
| 5 разных архитектур (RF + 4 NN) дают одинаковый потолок | F1_minority = 0.35–0.39, разброс 0.04 |
| BiLSTM конвергирует за 2–3 эпохи | best_epoch = 2–3, дальше только оверфиттинг |
| Все NN ≈ классический Random Forest | RF F1_minority=0.370, лучшая NN=0.385 |
| R² ≈ 0.30 для регрессии | 70% дисперсии не объясняется |

### Логика рассуждения

**Если 5 принципиально разных архитектур** (линейная, деревья, свёрточная, рекуррентная, attention-based) **дают одинаковый результат** — значит, ни одна из них не может извлечь из данных больше информации, чем уже извлечено.

Это называется **information ceiling** (потолок информации) в данных:

```
Реальный сигнал в данных → ~35% F1 для сигнальных классов → это всё, что можно достать
     ↑ Ограничение
     │
Никакая архитектура не поможет, потому что:
1. Слишком мало примеров сигнальных классов (~1000 из 43K)
2. Признаки слабо различают сигнал от нейтрали
3. Рынок объективно шумный — часть разворотов непредсказуема
```

### Что это значит практически

| Бесполезно делать | Полезно делать |
|-------------------|----------------|
| ❌ Пробовать новые NN архитектуры | ✅ Добавлять новые features (ME-3) |
| ❌ Усложнять модели (больше слоёв/параметров) | ✅ Переформулировать задачу (регрессия вместо классификации) |
| ❌ Тюнить loss/sampler для 3-классовой задачи | ✅ Собрать больше данных (>10K сигналов) |
| ❌ HPO для классификации | ✅ Ablation study — какие features полезны |

### Аналогия

Представьте фотографию низкого разрешения с шумом. Никакой алгоритм upscale не восстановит детали, которых в пикселях нет. Можно менять алгоритмы (bicubic, lanczos, AI upscale) — результат будет одинаково размытый. Чтобы получить лучшее изображение, нужна **другая камера** (лучшие данные) или **другой план** (другая постановка задачи).

Именно поэтому аудит рекомендует **переход к регрессии** — это «другой план», который обходит проблему данных, используя все 43K примеров вместо ~1000 сигнальных.
