## Диагностика 1: Oracle-ablation (прямой ответ «что хуже»)

Четыре прогона с подстановкой oracle/ML для breach и fav:

| Прогон | breach | fav | Ожидаемый PF | Что измеряет |
|--------|--------|-----|-------------|--------------|
| A | **oracle** | ML | ? | Потеря от fav-ошибок |
| B | ML | **oracle** | ? | Потеря от breach-ошибок |
| C | ML | ML | 1.106 | Текущий (известен) |
| D | **oracle** | **oracle** | ∞ | Уже известен |

- Если PF_A >> PF_B → **breach — узкое место** (даже с идеальным fav, ML breach слишком много пропускает пробоев)
- Если PF_B >> PF_A → **fav — узкое место** (даже с идеальный breach, шумный fav делает TP неточным)

Oracle breach = фильтр: `breach_flag == 0` → вход. Oracle fav = `target_sell_H6_val` вместо fav_pred для TP.

## Диагностика 2: Декомпозиция убытков

Разбить все убыточные сделки winner (`sell_H6_off05`) на категории:
- **SL (breach FN)**: стоп-бит, прогноз breach был < p, но стоп пробит → модель breach ошиблась
- **SL (ambiguous)**: стоп и TP в одном баре, принято SL
- **TIMEOUT с убытком**: модель breach верна (стоп не пробит), но TP не достигнут → fav завышена или ход недостаточен

Это покажет, какая доля убытков приходится на breach vs fav vs механику.

## Диагностика 3: Условный PF

Разрезать сделки winner по условиям:
- По quartile breach_prob: сделки с breach_prob < 0.2, 0.2–0.4, 0.4–0.5 → падает ли PF с ростом ошибки breach?
- По quartile fav_pred: высокая fav → больше ли TP-хитов?
- По ATR regime: низкая/высокая волатильность → лучше/хуже модель?
- По часу/дню недели: есть ли часы с PF > 1.5?

Каждый срез — кандидат на дополнительный фильтр.

## Дополнительные условия (фильтры)

На основе диагностики 3, возможные фильтры входа:

1. **Ужесточение p-порога**: breach_prob < 0.2 вместо 0.4 → меньше ложных входов, но меньше сделок
2. **Fav confidence**: ensemble variance fav — низкая дисперсия → более точный TP → вход
3. **ATR-фильтр**: только при ATR > медианы — в узких рынках фракталы шумнее
4. **Breakeven-stop**: перенос SL в безубыток после достижения +1×risk → сокращение убытков от timeout
5. **Dynamic TP**: tp_fraction = quantile(fav_pred, 0.5) вместо фиксированного 0.4

## Порядок действий

Приоритет: диагностика 1 (oracle-ablation) → декомпозиция убытков → условный PF → фильтры.
