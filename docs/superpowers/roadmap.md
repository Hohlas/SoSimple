## Будущие памятки после текущего плана


### 0. Следующий возможный шаг:
отдельный confirmatory cycle вокруг structure_full и одного короткого horizon (H3 или H6) с заранее замороженным mapping up_h/dn_h -> trading decision.

### 1. Regression Up/Dn feature expansion

**Когда возвращаться:** только после завершения текущего плана
`Regression Up/Dn target foundation` и только если он покажет, что хотя бы один
горизонт `up_*/dn_*` заслуживает дальнейшей проверки.

**Задача:** проверить, усиливают ли найденную `up/dn`-цель близкие по природе
признаки и ценовое положение, не смешивая это с новым широким поиском target.

**Обязательные группы признаков для следующего плана:**

- `token_updn`: `fractal*.up_3/dn_3`, `fractal*.up_6/dn_6`,
  `fractal*.up_12/dn_12`, `fractal*.up_24/dn_24`,
  `fractal*.up_48/dn_48`;
- `price_position`: положение `fractal0.price`, расстояние цен других фракталов
  до `fractal0.price` в ATR, `absolute price/ATR`, `relative price`;
- `geometry_price`: ограниченный набор `nearest40`, `corridor`,
  `relative geometry`.

**Ограничения:**

- не запускать этот этап, если foundation не нашёл живую `up/dn`-цель;
- не проверять все горизонты заново: брать только горизонты, прошедшие
  foundation gate или явно отмеченные как сильный диагностический след;
- `fractal*.up/dn` и ценовые признаки проверять как добавку к уже найденной
  основе, а не как замену target contract;
- не выбирать winner по `diagnostic_holdout` или `low_n_disclosure`;
- разделить результаты по группам: отдельно `token_updn`, отдельно
  `price_position`, отдельно `geometry_price`, затем ограниченные combined
  профили;
- если XGBoost даёт устойчивый сигнал, отдельным следующим планом проверить
  Transformer как sequence-модель. Не начинать feature expansion с Transformer.

**Почему не в текущем foundation:** текущий этап отвечает, предсказуемы ли
сами `up/dn`-цели. Feature expansion отвечает другой вопрос: какие группы
признаков дают прирост к уже найденной цели.

Статус: следующий возможный план после foundation, если foundation не провален.

### 2. Transformer follow-up for Regression Up/Dn

**Когда возвращаться:** только если XGBoost/простые baseline на `up/dn`-целях
показали устойчивый сигнал и есть понятный горизонт/профиль для сравнения.

**Задача:** проверить, даёт ли Transformer пользу за счёт последовательности
фракталов, а не просто усложняет модель.

**Ограничения:**

- Transformer не должен быть первым доказательством живой цели;
- сравнивать только с тем же target, split и feature contract, где уже есть
  сильный табличный baseline;
- если Transformer выигрывает только на aggregate-метрике, но проигрывает по
  годам, seed или block bootstrap, результат остаётся диагностическим.

Статус: отложено до появления устойчивого табличного сигнала.

### 3. Мульти-актив / мульти-таймфрейм валидация

Проверить fractal-концепт на другом инструменте или таймфрейме. Независимая
проверка без новых данных по XAUUSD. Но: нужны новые данные, большой объём
работы, не отвечает на ближайший вопрос о новом источнике сигнала для H12 на
XAUUSD. Слишком дорого для текущего этапа.

Статус: отложено до появления подтверждённого сигнала или необходимости
проверить переносимость результата.

## Отложенные незавершённые направления

### Central multi-profile inference service

**Контекст:** текущий online-контур исторически опирался на отдельный watcher для
связки `Nero.csv -> ml_signals.csv`. Если снова появится несколько live-safe
runtime-профилей, ручной запуск отдельных процессов станет операционным риском.

**Задача:** заменить ручной single-profile watcher одним управляемым Python-сервисом,
который по конфигу обслуживает несколько runtime-профилей: входной `Nero*.csv`,
checkpoint, frozen rule, output `ml_signals*.csv`, state/log/metadata.

**Выход:** managed service без обязательного `tmux`, при сохранении текущего
Python training/inference pipeline и совместимости с Strategy Tester через CSV
exports.

Design note: [2026-04-28-central-inference-service-design.md](specs/2026-04-28-central-inference-service-design.md)

Статус: есть дизайн, отчёт о реализации центрального multi-profile сервиса не
найден.

### Risk filters only after system discovery

**Контекст:** фильтры поверх уже найденного сигнала часто сокращают сделки и
повышают риск подгонки.

**Задача:** применять риск-фильтры только после того, как найден самостоятельный
источник прибыли или стабильный диагностический сигнал.

**Выход:** отдельный bounded benchmark для фильтра, где заранее ограничены число
правил и критерии успеха.

Статус: отложенный принцип для будущих торговых кандидатов; сейчас не является
ближайшим исследовательским шагом.
