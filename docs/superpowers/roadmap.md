## Главный порядок работ

### Контекст после Stage 5.3

Stage 5.1-5.3 завершены с вердиктом `DIAGNOSTIC_ONLY`: это диагностическая
ветка, не торговый кандидат. Установленные факты:

1. **Фрактальный сигнал существует.** `structure_only` стабильно выше `time_only`
   (sell +0.036…+0.071, buy +0.017…+0.050). Это не календарь.
2. **Price/ATR токены — шум.** Удаление price/ATR не вредит, иногда улучшает AUC
   (12 из 18 сравнений `structure_only` ≥ `base_raw_plus_time`).
3. **H6_off05 как старая бинарная цель исчерпана.** 8+ этапов: кодирование
   (5.0d), модель (5.0c/e), временное окно (5.0f), абляция полей (5.1/5.1b) —
   прорыва нет. AUC 0.65-0.70, умеренный, деградирует на сложных годах.
4. **H2 (temporal decay) скорее опровергнута.** `fixed` > `rolling`
   (sell 6/6 лет, buy 4/6). Старые данные не вредят.
5. **H1 (слабый сигнал) не подтверждена.** Некоторые AUC > 0.68 — сигнал не
   uniformly слабый.
6. **2023-2025 сожжены** для диагностического решения по `H6_off05`.
7. **`back` — единственное устойчивое структурное поле** (`overall_likely_useful`
   на обеих целях, survives добавление `shift` в baseline). `impulse` — второй
   кандидат, но не получает самостоятельный useful verdict. Up/Dn поля не
   улучшают `structure_full` и не обязательны для следующего шага.
8. **`back + impulse` почти догоняет `structure_full`** на sell и превосходит
   на buy, но это diagnostic control, не подтверждённый кандидат.
9. **Обычная регрессия времени до пробоя не стала кандидатом.** Stage 5.2
   показал ранжирование (`clock_shift_back`/`clock_shift_back_impulse`), но MAE
   хуже константы `7`, а oracle-PF сравнение невалидно.
10. **Дискретная цель `fast` дала полезный диагностический сигнал.** Stage 5.3
    показал, что ранний пробой (`bars_to_breach ∈ {1,2}`) отделяется лучше, чем
    старый binary breach baseline: sell `fast` проходит gate, buy `fast`
    пограничен и держится только на 1/3 seed по порогу `delta ≥ 0.02`.
11. **Stage 5.3 закрыл ось "постановка цели", но не ось новых признаков.**
    `price_coord_atr`, `price_atr_scaled`, raw `ATR`, Up/Dn и новые price-группы
    в Stage 5.3 не добавлялись.

Полные детали:
`docs/reports/2026-06-25-stage5_1b-updn-field-ablation.md`,
`docs/reports/2026-06-25-stage5_2-time-to-breach-regression.md`,
`docs/reports/2026-06-26-stage5_3-time-to-breach-target-reformulation.md`.

### 1. Stage 5.4 — price-coordinate / ATR ablation вокруг `fast`

**Контекст:** Перед Stage 5.3 были развилки: диагностика vs кандидат,
`breach_after_k`/bucket vs `survives_at_least_k`, факторный дизайн vs широкий
перебор, survival-loss сейчас или позже. Фактически выполнен факторный
диагностический шаг по оси **целей**: `breach_after_k2..k5`,
`fast`/`medium`/`no_breach`, controls `survives_at_least_k`. Лучшей family стала
`fast`. Ось **новых признаков** ещё не проверена.

**Задача:** зафиксировать target family `fast` и проверить только узкую ось
признаков:

1. baseline: текущие `clock_shift_back` и `clock_shift_back_impulse`;
2. `+price_coord_atr = (price - f0_price) / ATR`;
3. `+price_atr_scaled = price / ATR`, только если A7-аудит распределений не
   показывает недопустимый сдвиг;
4. optional diagnostic: `+Up/Dn` как отдельная группа, не в baseline.

**Выход:** понять, был ли следующий недостающий сигнал физическим расстоянием до
уровня, а не новой моделью или новым поиском цели.

**Ограничения:**
- статус: диагностика, не кандидат;
- target family фиксирована: `fast`;
- sell — основная проверка, потому что прошёл Stage 5.3 gate;
- buy — пограничный disclosure, потому что `delta ≥ 0.02` прошёл только 1/3
  seed;
- `2023-2025` остаются diagnostic disclosure;
- не смешивать новый target search и feature search;
- не использовать `survives_at_least_k` как winner;
- не добавлять Up/Dn по умолчанию.

Статус: ближайший рекомендуемый шаг, если продолжать Fractal Stop.

### Закрытые недавние этапы

**Stage 5.2 — time-to-breach regression.** Проверил обычную регрессию
`bars_to_breach`. Ранжирование есть, `back` снова полезен, но MAE хуже constant
baseline `7`, а oracle-PF сравнение невалидно. Вердикт: `DIAGNOSTIC_ONLY`.

**Stage 5.3 — target reformulation.** Проверил дискретные цели
`breach_after_k`, `fast`/`medium`/`no_breach` и controls `survives_at_least_k`.
Лучший main target — `fast`. Sell проходит gate; buy пограничен. Вердикт отчёта:
`DIAGNOSTIC_ONLY`, JSON status `TARGET_REFORMULATION_FOUND` означает только
разрешение на следующий диагностический шаг.

### Альтернативные направления (не рекомендуются как ближайший шаг)

**3. Уход от Fractal Stop к regression_updn / triple barrier.**
Совершенно другая парадигма разметки. Чистый старт, независимый от сожжённых
фрактальных данных. Но: значительная новая инфраструктура, теряет контекст
фракталов, нет гарантии что сигнал там сильнее. После Stage 5.3 этот вариант
менее срочный: есть evidence, что проблема была не только в признаках, но и в
постановке цели — `fast` даёт delta над binary baseline, особенно на sell.
Рассматривать, если Stage 5.4 не подтвердит, что price-coordinate/ATR усиливает
`fast`, или если будущий независимый период не подтвердит sell `fast`.

**4. Мульти-актив / мульти-таймфрейм валидация.**
Проверить fractal-концепт на другом инструменте или таймфрейме. Независимая
проверка без новых данных по XAUUSD. Но: нужны новые данные, большой объём
работы, не отвечает на вопрос «что делать с H6_off05 на XAUUSD». Слишком дорого
для текущего этапа.

**5. Новый большой перебор по H6_off05.**
Не оправдан: 2023-2025 сожжены, природа отрицательного результата не
установлена и не установится без новых данных. H2 опровергнута, H1 не
подтверждена — дальнейшая настройка на том же таргете не даст нового знания.

## Отложенные незавершённые направления

### Central multi-profile inference service

**Контекст:** текущий online-контур исторически опирался на отдельный watcher для
связки `Nero.csv -> ml_signals.csv`. Если снова появится несколько live-safe
runtime-профилей, ручной запуск отдельных процессов станет операционным риском.

**Задача:** заменить ручной single-profile watcher одним управляемым Python-сервисом,
который по конфигу обслуживает несколько runtime-профилей: входной `Nero*.csv`,
checkpoint, frozen rule, output `ml_signals*.csv`, state/log/metadata.

**Выход:** managed service без обязательного `tmux`, при сохранении текущего
Python training/inference pipeline и совместимости с Strategy Tester через CSV
exports.

Design note: [2026-04-28-central-inference-service-design.md](specs/2026-04-28-central-inference-service-design.md)

Статус: есть дизайн, отчёт о реализации центрального multi-profile сервиса не
найден.

### Risk filters only after system discovery

**Контекст:** фильтры поверх уже найденного сигнала часто сокращают сделки и
повышают риск подгонки.

**Задача:** применять риск-фильтры только после того, как найден самостоятельный
источник прибыли или стабильный диагностический сигнал.

**Выход:** отдельный bounded benchmark для фильтра, где заранее ограничены число
правил и критерии успеха.

Статус: отложенный принцип для будущих торговых кандидатов; сейчас не является
ближайшим исследовательским шагом.
