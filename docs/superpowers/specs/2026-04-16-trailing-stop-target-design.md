# Trailing-Stop Target Retraining Design

> **Date**: 2026-04-16
> **Status**: Draft
> **Track**: Новый трек обучения после исчерпания Track A max-out
> **Goal**: Проверить, даст ли новая непрерывная целевая переменная, построенная на простом исполнимом выходе `stop = trailing_stop = X * ATR`, рабочую зону `PF > 1` на validation
> **Related materials**: `docs/reports/2026-04-15-track-a-max-out.md`, `docs/reports/2026-04-12-quantile-status-decision.md`, `docs/superpowers/plans/2026-04-07-outcome-aligned-retraining.md`

## Context

`Track A max-out` подтвердил важный отрицательный результат:

- richer features помогли;
- более длинное обучение помогло;
- `seq_len=20/50` оказались лучше короткого baseline;
- но даже лучший run не дошёл до `PF > 1` на validation.

Это означает, что следующий шаг должен менять не слой отбора поверх старой модели, а саму постановку задачи обучения.

Ключевое требование к новому треку:

- цель должна быть исполнимой в реальной торговой системе;
- цель не должна опираться на недостижимый "идеальный максимум";
- логика выхода должна оставаться простой и робастной.

Из этих требований следует новый design: вместо старых target-ов модель учится предсказывать результат сделки при очень простой логике выхода, где один и тот же параметр `X` служит и стопом, и трейлинг-стопом.

## Main Idea

Новый трек строится вокруг path-dependent, но исполнимой непрерывной цели.

Логика сделки:

- после входа фиксируется `ATR` в точке входа;
- затем в течение ограниченного окна наблюдения ведётся лучший достигнутый ход цены в сторону сделки;
- если откат от этого лучшего хода достигает `X * ATR`, сделка считается закрытой;
- если такого отката не было до конца окна, сделка закрывается по последней цене окна.

Эта схема намеренно проста:

- один параметр `X`;
- без отдельной активации трейлинга;
- без отдельного timeout-штрафа;
- без нескольких степеней свободы в первой версии.

Идея не в том, чтобы построить "самый умный" выход, а в том, чтобы обучать модель на результате стратегии, которую потом действительно можно повторить в production.

## Target Design

### New Target Family

Для каждого фиксированного `X` строится отдельная непрерывная целевая переменная:

- `trail_48_pnl_atr_x2`
- `trail_48_pnl_atr_x3`
- `trail_48_pnl_atr_x5`

Смысл каждой переменной:

- фактический итог сделки в единицах `ATR`,
- если сделка живёт не дольше `48` баров,
- и закрывается по правилу `stop = trailing_stop = X * ATR`.

### Labeling Rule

Правило расчёта для long:

1. взять цену входа и `ATR` входа;
2. на каждом следующем баре обновлять лучший достигнутый максимум цены в сторону сделки;
3. считать текущий откат от этого максимума;
4. если откат стал не меньше `X * ATR`, фиксировать выход;
5. если за `48` баров это не произошло, закрывать сделку по последней доступной цене окна.

Для short используется симметричное правило.

Полученный итог сделки нормируется на `ATR` входа и записывается как target.

### Why This Target

Этот target сохраняет важные свойства:

- учитывает путь цены, а не только итог на фиксированном горизонте;
- не требует знания недостижимого максимума прибыли;
- напрямую связан с исполнимой торговой логикой;
- достаточно прост, чтобы сохранить робастность и не превратиться в search over many knobs.

## X Family Design

### Why Not One Fixed X

Один фиксированный `X` был бы слишком хрупким решением:

- если значение случайно неудачное, можно ложно отвергнуть весь трек;
- при этом делать плотный sweep по множеству `X` тоже нельзя, иначе исследование быстро превратится в подгонку.

### Chosen Family

Первое bounded family:

- `X = 2`
- `X = 3`
- `X = 5`

Причины выбора:

- `2` — относительно плотный, но уже не шумовой уровень для H1;
- `3` — центральный базовый вариант;
- `5` — более широкий вариант, который позволяет сделке "дышать" и проверяет, есть ли ценность в более долгом удержании.

Эти три значения дают достаточно широкий диапазон без перехода в бесконтрольный search.

## Model Design

### First Pass Scope

Первый проход intentionally ограничен.

Используется только:

- текущий `EntryPathTransformer`.

Не используются:

- `dual_stream`;
- дополнительные новые архитектуры;
- отдельный architecture sweep.

### Why Only One Model

В первом проходе проверяется прежде всего новая целевая постановка.

Если одновременно менять:

- target,
- архитектуру,
- benchmark families,

то станет невозможно понять, что именно реально сработало или не сработало.

Поэтому первый этап должен быть максимально чистым:

- одна архитектура;
- новая цель;
- несколько длин истории;
- несколько фиксированных `X`.

## Sequence-Length Policy

Новый трек сразу сравнивает три длины истории:

- `seq_len = 20`
- `seq_len = 50`
- `seq_len = 100`

Причина проста:

- в предыдущем этапе уже было видно, что длина контекста заметно влияет на результат;
- новый target может вести себя иначе, чем старый `entry_path_v1`.

Поэтому длина истории входит в первый bounded matrix и не откладывается "на потом".

## Training Matrix

Первый честный прогон нового трека:

- модель: `EntryPathTransformer`
- `X ∈ {2, 3, 5}`
- `seq_len ∈ {20, 50, 100}`

Итого:

- `9` run-ов

Это и есть полный scope первой волны.

Не делаются:

- дополнительные architecture variants;
- отдельные runs с альтернативными loss families;
- широкий sweep seed-ов до появления хотя бы одного рабочего validation signal.

## Evaluation Policy

Оценка делится на два слоя.

### 1. Regression Diagnostics

Вспомогательные метрики:

- `pearson_r`
- `MAE`
- `RMSE`
- знак результата как вспомогательная диагностика направления

Эти показатели важны, но они не выбирают победителя сами по себе.

### 2. Validation-First Trading Benchmark

Главный выбор победителя идёт через торговый benchmark по prediction exports.

Первый benchmark должен быть коротким и строгим.

Разумный первый набор candidate families:

- `pred_trail_only`
- `pred_trail_over_pred_adv24`
- `pred_trail_minus_lambda * pred_adv24`

Если нужно ещё сильнее ограничить этап, допустимо начать даже с одного семейства:

- `pred_trail_only`

Но базовая рекомендация — не больше трёх простых семейств без возврата к большому search space.

### Benchmark Metrics

Обязательные метрики:

- `PF`
- `trades_per_year`
- `negative_year_slices`
- `profit_concentration_top_10`
- `ulcer_index`
- `max_drawdown_atr`

### Selection Rule

Правило выбора строгое:

- winner выбирается только на validation;
- test открывается только для validation winner;
- если нет ни одного validation candidate с `PF > 1`, это считается честным отрицательным результатом первой волны.

## Success Criteria

Первая волна считается успешной, если найден хотя бы один validation candidate, который:

- даёт `PF > 1`;
- не разваливается по крупным временным срезам;
- не держится на нескольких случайных сделках;
- сохраняет приемлемую частоту сделок;
- не ломается полностью на frozen test-check.

Успех не требует production-level результата.
На этом этапе достаточно показать, что новая цель вообще создаёт рабочую зону лучше исчерпанного Track A.

## Failure Criteria

Первая волна считается неуспешной, если после всех `9` run-ов:

- ни один validation candidate не доходит до `PF > 1`;
- или лучшие варианты держатся только на шуме;
- или test полностью ломает validation result.

В таком случае следующий шаг — уже не ещё один cosmetic retrain, а более глубокий пересмотр:

- alternative objective family;
- ranking formulation;
- binary trade-worthiness formulation.

## Risks

Основные риски нового трека:

- even execution-aware target может остаться слишком шумным;
- `X=2/3/5` может оказаться всё ещё не лучшим bounded family;
- большие `seq_len` могут снова добавлять шум вместо полезного контекста;
- benchmark слишком быстро может начать тяготеть к одному "least bad" family, если не держать candidate set коротким.

Поэтому bounded scope — критическая часть design, а не формальность.

## Implementation Outline

1. Добавить новый family target-ов в labeling layer.
2. Протянуть его через task contract и data loader.
3. Обновить train/evaluate/export pipeline для новой целевой переменной.
4. Добавить короткий benchmark для нового track-а.
5. Выполнить matrix `3 X values × 3 seq_len values`.
6. Выбрать winner только на validation.
7. Сделать один frozen test-check.
8. Зафиксировать verdict по первой волне нового трека.

## Decision

Решение по design:

- следующий research-trек меняет сам objective обучения;
- цель строится на простом исполнимом trailing-stop output;
- первый проход deliberately ограничен матрицей `9` run-ов;
- если даже этот objective не даёт `PF > 1` на validation, нужно будет идти уже к следующему family целей, а не дожимать ту же идею бесконечным search.
