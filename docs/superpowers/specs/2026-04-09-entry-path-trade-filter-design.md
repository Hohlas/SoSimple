# Entry Path Trade Filter v1 — Design Spec

> **Date**: 2026-04-09
> **Status**: Draft
> **Track**: Параллельный слой поверх `entry_path_v1`
> **Goal**: Построить первый слой `торговать / не торговать` поверх текущего `entry_path_v1` и честно сравнить простой и составной варианты отбора

---

## 1. Context

Для `entry_path_v1` уже выбран рабочий базовый вариант обучения:

- active rows получают вес `5.0` в `ret_*` и `path_6_class`
- validation: `ret_pearson_r=0.2736`, `path_reg_pearson_r=0.3006`, `path_cls_f1_macro=0.4059`
- test: `ret_pearson_r=0.2494`, `path_reg_pearson_r=0.2722`, `path_cls_f1_macro=0.4160`
- active-only test: `ret_pearson_r=0.2285`

Следующий шаг уже не в новом подборе весов. Теперь нужно понять, можно ли поверх этих прогнозов построить первый разумный слой `торговать / не торговать`.

На этом этапе задача не в том, чтобы сразу получить готовую торговую систему. Задача в том, чтобы проверить: добавляет ли слой отбора качество сделок и какой тип отбора лучше подходит как база для следующего шага.

---

## 2. Main Idea

Нужно сравнить два варианта фильтра:

1. **Кандидат A** — простой фильтр только по `pred_ret_24_dir_atr`
2. **Кандидат B** — составной фильтр по нескольким выходам модели

Оба фильтра:

- настраиваются только на `validation`
- сначала подбираются так, чтобы оставлять примерно `70%` активных сигналов
- потом замораживаются
- затем честно проверяются на `test`

Главная цель сравнения:

1. сначала качество сделок после отбора
2. потом устойчивость по годам
3. и только потом доля оставшихся сделок

---

## 3. Scope

### Входит в этап

- два кандидата фильтра `торговать / не торговать`
- единая validation-only процедура подбора порога
- единый benchmark для сравнения фильтров
- основная проверка по сигналам по отдельности
- дополнительная проверка в последовательном режиме

### Не входит в этап

- новый retrain `entry_path_v1`
- замена таргетов
- перенос фильтра в MT4
- подбор размера позиции
- SL/TP, trailing, pullback
- полноценная торговая система

---

## 4. Design Principles

### 4.1. Сначала простой benchmark, потом усложнение

Нельзя сразу строить сложный слой отбора и потом гадать, помогает ли он вообще. Поэтому первым всегда должен быть понятный простой кандидат.

### 4.2. Одинаковые правила сравнения

Кандидаты A и B должны сравниваться на одной и той же основе:

- один и тот же набор активных сигналов
- один и тот же ориентир по coverage
- одна и та же последовательность метрик

### 4.3. Validation-first

Все настройки фильтра подбираются только на `validation`. `test` используется только как финальная проверка.

### 4.4. Мягкий первый отбор

Первый рабочий слой должен быть мягким. Цель около `70%` активных сигналов выбрана специально:

- оставить достаточно сделок
- сохранить пространство для будущей дополнительной фильтрации
- не делать слишком жёсткий отбор слишком рано

### 4.5. Отдельно сигнал и отдельно исполнение

Основная проверка должна идти по сигналам по отдельности. Последовательный режим нужен как вторичная проверка, а не как главный критерий выбора.

---

## 5. Candidate A — Simple Filter

### 5.1. Источник score

Кандидат A использует только:

- `pred_ret_24_dir_atr`

### 5.2. Логика

Чем выше `pred_ret_24_dir_atr`, тем сильнее модель считает идею полезной.

На `validation` выбирается такой порог, чтобы осталось примерно `70%` активных сигналов.

### 5.3. Зачем он нужен

Это базовая линия для сравнения. Если составной фильтр B не сможет заметно улучшить A, то сложность B не оправдана.

---

## 6. Candidate B — Composite Filter

### 6.1. Какие поля входят

В составной score входят:

- `pred_ret_24_dir_atr`
- `pred_ret_12_dir_atr`
- `pred_fav_12_atr - pred_adv_12_atr`
- `pred_fav_24_atr - pred_adv_24_atr`
- `pred_path_6_prob_pos - pred_path_6_prob_neg`

Для краткости:

- `ret24`
- `ret12`
- `edge12`
- `edge24`
- `path6`

### 6.2. Какие поля не входят в v1

В первый составной фильтр специально не входят:

- `ret_6_dir_atr`
- `fav_6_atr`
- `adv_6_atr`

Причина простая: для H1 они выглядят более шумными и могут сильнее мешать, чем помогать.

### 6.3. Формула score

Первый вариант составного score:

```text
score_B =
  0.45 * ret24 +
  0.20 * ret12 +
  0.15 * edge12 +
  0.10 * edge24 +
  0.10 * path6
```

Где:

```text
edge12 = pred_fav_12_atr - pred_adv_12_atr
edge24 = pred_fav_24_atr - pred_adv_24_atr
path6  = pred_path_6_prob_pos - pred_path_6_prob_neg
```

### 6.4. Нормализация

Перед сборкой `score_B` все входные величины на `validation` приводятся к одной шкале.

Для `v1` берётся простая rank-based схема:

- на активных строках `validation` для каждого поля считается percentile rank в диапазоне `[0, 1]`
- для `test` каждое значение маппится через ту же validation-распределённую шкалу, без подглядывания в `test`

Причина выбора:

- схема устойчива к выбросам
- не требует предположений о форме распределения
- хорошо подходит для простого составного score

---

## 7. Coverage Target

Оба кандидата A и B сначала настраиваются на одинаковую цель:

- оставить примерно `70%` активных сигналов

Это не должно пониматься как жёсткое магическое число. Это стартовый ориентир для первого слоя отбора.

Допустимое практическое окно:

- около `65%–75%`

Если точное `70%` недостижимо из-за дискретности порогов, берётся ближайшее разумное значение.

---

## 8. Evaluation Protocol

### 8.1. Основная проверка

Главная проверка идёт по сигналам по отдельности.

Это значит:

- каждый активный сигнал оценивается сам по себе
- без смешивания с правилами открытия одной позиции, блокировкой и прочими ограничениями исполнения

### 8.2. Дополнительная проверка

После выбора кандидата по основной проверке делается вторичная проверка в последовательном режиме.

Её задача:

- понять, не исчезает ли польза фильтра, когда сигналы начинают конкурировать друг с другом

Но этот режим не должен решать исход сравнения A vs B, если основной benchmark уже говорит обратное.

### 8.3. Проверка устойчивости по времени

Устойчивость считается по той же простой схеме, которая уже используется в проекте для outcome-benchmark:

- сначала период режется по календарным годам
- в зачёт идут только те годы, где после фильтра осталось не меньше `10` сделок
- для каждого такого года считается `PF`
- `stability_ratio = stable_years / eligible_years`, где стабильный год — это год с `PF >= 1.0`
- дополнительно сохраняется `worst_year_pf`

Если в выборке после фильтра нет хотя бы двух зачётных лет, делается запасной разрез по полугодиям с тем же правилом `>= 10` сделок на период.

---

## 9. Ranking Rules

Кандидаты сравниваются в таком порядке:

1. качество сделок после отбора
2. устойчивость по годам
3. доля оставшихся сделок

Практически это означает:

- если один фильтр заметно лучше по качеству, он выигрывает
- если качество близко, выигрывает более устойчивый
- если и это близко, выигрывает фильтр с большей долей сделок

---

## 10. Expected Outputs

Новый слой должен давать:

- validation-report по A и B
- замороженный выбор победителя
- test-report по победителю
- отдельный блок по coverage
- отдельный блок по active-only качеству
- отдельный блок по последовательной проверке

---

## 11. Success Criteria

Этап можно считать успешным, если:

1. оба кандидата A и B честно настроены только на `validation`
2. сравнение сделано по одним и тем же правилам
3. выбран победитель
4. его `test`-результат не хуже текущего рабочего базового варианта по смыслу задачи
5. вывод понятен: какой фильтр брать дальше и почему

---

## 12. Deferred Topics

В этом spec сознательно не включены в `v1`, но могут стать следующим шагом:

- второй coverage target, например около `50%`
- слой conformal prediction поверх уже выбранного победителя
- более сложный составной score, если простой `A` и текущий `B` окажутся слишком близки
