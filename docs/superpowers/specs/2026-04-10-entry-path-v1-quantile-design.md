# Entry Path v1 Quantile — Design Spec

> **Date**: 2026-04-10
> **Status**: Draft
> **Track**: Расширение рабочего `entry_path_v1`
> **Goal**: Добавить quantile-головы к уже рабочему `entry_path_v1`, чтобы модель одновременно сохраняла полезный ranking сигналов и строила нижнюю/верхнюю границу для `ret_24_dir_atr`

---

## 1. Context

Для `entry_path_v1` уже подтверждён рабочий базовый слой отбора:

- winner: `A @ 7.5%`
- validation: `36 trades`, `PF=2.67`
- test: `44 trades`, `PF=4.29`
- последовательная проверка: `30 trades`, `PF=2.87`

После этого были проверены три отдельных пути для confidence-слоя:

1. простой `split conformal` поверх базы
2. adaptive conformal с отдельной моделью ошибки
3. отдельный quantile-трек `entry_path_quantile_v1`

Все три варианта не дали улучшения.

Самый важный вывод последнего этапа:

- отдельный quantile-трек оказался слишком слабым даже после перевода на активные строки `signal != 0`;
- на active-only данных он всё равно не держал полезную шкалу `ret_24`;
- поверх базы `A @ 7.5%` все правила вида `LB > 0` давали `0` сделок.

Это означает, что проблема не решается отдельной узкой моделью для quantile-границ. Значит, новые границы нужно учить рядом с тем представлением, которое уже умеет ранжировать сделки.

---

## 2. Main Idea

Новый трек `entry_path_v1_quantile` должен быть не заменой `entry_path_v1`, а его расширением.

Что сохраняется:

- все текущие сильные головы `entry_path_v1`
- текущая логика ranking и отбора сигналов

Что добавляется:

- две новые головы для `ret_24_dir_atr`:
  - `ret_24_q10`
  - `ret_24_q90`

Смысл этапа:

- не строить quantile-модель отдельно с нуля;
- а дать quantile-головам учиться на том же sequence-представлении, которое уже полезно для signal ranking;
- затем поверх этих встроенных границ снова проверить слой `trade / no-trade`.

---

## 3. Scope

### Входит в этап

- новый task `entry_path_v1_quantile`
- новая модель на базе текущего `entry_path_v1` с двумя дополнительными quantile-головами
- обучение старых и новых голов в одном треке
- active-only расчёт quantile-loss
- export `validation/test` с полным набором старых выходов плюс `q10/q90`
- conformal-коррекция поверх `q10/q90`
- benchmark слоя `trade / no-trade` поверх нового трека
- сравнение с текущей базой `A @ 7.5%`

### Не входит в этап

- удаление или переписывание `entry_path_v1`
- новый набор таргетов
- перенос нового трека в MT4
- размер позиции
- trailing, pullback, SL/TP-политика
- новый trade-filter без quantile-границ

---

## 4. Design Principles

### 4.1. Не ломать рабочую базу

Главный риск нового этапа в том, что quantile-часть может испортить уже рабочий ranking сигналов.

Поэтому:

- старые головы `entry_path_v1` остаются первичными;
- quantile-головы добавляются как расширение, а не как новая главная задача.

### 4.2. База должна оставаться сильнее интервала

Нам не нужен “красивый интервал”, если при этом ломается текущий фильтр сделок.

Поэтому новый checkpoint не должен выбираться только по quantile-метрикам.

### 4.3. Только active-only для quantile-loss

Quantile-границы нельзя считать на строках `signal=0`, потому что прошлый этап уже показал, что это убивает задачу и сводит всё к почти постоянному нулю.

Поэтому:

- quantile-loss считается только на BUY/SELL строках;
- старые головы живут в своём рабочем режиме.

### 4.4. Validation-first

Все настройки выбираются только на `validation`:

- лучший checkpoint
- conformal-поправка
- winner для `trade / no-trade`

`test` остаётся только финальной проверкой.

---

## 5. Task Design

### 5.1. Новый task

Новый task:

- `entry_path_v1_quantile`

Он должен жить отдельно от `entry_path_v1`, чтобы:

- честно сравнивать старый и новый треки;
- не загрязнять старый baseline;
- при неудаче легко остановить новый путь.

### 5.2. Какие головы сохраняются

В новом task сохраняются все текущие головы `entry_path_v1`:

- `ret_6_dir_atr`
- `ret_12_dir_atr`
- `ret_24_dir_atr`
- `fav_6_atr`, `adv_6_atr`
- `fav_12_atr`, `adv_12_atr`
- `fav_24_atr`, `adv_24_atr`
- `path_6_class`

### 5.3. Какие головы добавляются

Добавляются две новые головы:

- `ret_24_q10`
- `ret_24_q90`

Точечный `ret_24` не выносится в отдельную особую ветку. Он остаётся частью текущего рабочего блока `ret_*`.

---

## 6. Model Design

### 6.1. Общая схема

Новая модель должна переиспользовать сильную часть `entry_path_v1`:

- тот же encoder
- та же общая sequence-логика
- те же рабочие головы

И затем добавлять:

- отдельную маленькую ветку для `ret_24_q10`
- отдельную маленькую ветку для `ret_24_q90`

### 6.2. Почему не отдельный узкий quantile-трек

Этот путь уже был честно проверен и не сработал.

Значит, проблема была не только в loss или в benchmark, а в том, что отдельному quantile-треку не хватило полезного общего представления.

### 6.3. Разделение файлов

Рекомендуемое разбиение:

- отдельная модель, например `ML/models/entry_path_v1_quantile_transformer.py`
- отдельный task-модуль, например `ML/entry_path_v1_quantile_task.py`

И доработки в:

- `ML/data_loader.py`
- `ML/train.py`
- `ML/evaluate_test.py`
- benchmark-модуле нового этапа

Отдельный файл модели нужен затем, чтобы не превращать существующий `entry_path_transformer.py` в слишком перегруженный гибрид.

---

## 7. Loss Design

### 7.1. Старые головы

Все старые головы `entry_path_v1` должны сохранять текущую рабочую схему loss.

То есть новый этап не должен менять уже подтверждённую логику обучения старого трека без необходимости.

### 7.2. Новые quantile-головы

Для новых голов:

- `ret_24_q10`: pinball loss с `q=0.1`
- `ret_24_q90`: pinball loss с `q=0.9`

### 7.3. Где считать quantile-loss

Quantile-loss считается только на строках:

- `signal != 0`

Это жёсткое правило этапа.

### 7.4. Общая loss-схема

Первая рабочая схема должна быть умеренной:

```text
loss_total =
  entry_path_v1_working_loss
  + w_q * q10_loss_active
  + w_q * q90_loss_active
```

Где:

- `entry_path_v1_working_loss` — текущая рабочая loss-схема старого трека
- `w_q` — умеренный вес quantile-голов

Цель здесь не в том, чтобы quantile-часть доминировала, а в том, чтобы она училась от уже полезного backbone.

---

## 8. Checkpoint Selection

### 8.1. Главный принцип

Лучший checkpoint не должен выбираться только по интервалу.

Если новый checkpoint улучшает quantile-метрики, но ломает ranking и trade-filter, он плохой.

### 8.2. Mixed validation score

Для выбора checkpoint нужен смешанный критерий:

- сначала должен держаться рабочий уровень старых `entry_path_v1`-метрик;
- затем добавляется quantile-штраф за плохое покрытие;
- затем мягкий штраф за слишком широкую границу.

Практический смысл:

- ranking сигналов остаётся главной частью;
- quantile-часть должна улучшать модель, а не перетягивать её в сторону “широких безопасных интервалов”.

### 8.3. Что логировать

В `result.json` нового task должны попасть:

- рабочие метрики старого `entry_path_v1`
- quantile coverage
- median interval width
- mixed `val_score`

---

## 9. Evaluation Flow

### 9.1. Export

На `validation/test` новый task должен выпускать CSV, где есть:

- старые `entry_path_v1`-выходы
- `pred_ret_24_q10`
- `pred_ret_24_q90`

### 9.2. Conformal

После выбора лучшего checkpoint:

- на `validation` считается conformal-поправка поверх `q10/q90`;
- затем строятся:
  - `LB`
  - `UB`
  - `width`

### 9.3. Trade / No-Trade

После этого поверх уже скорректированных границ снова проверяются правила:

- `LB > 0`
- `LB > m`
- `LB > m` и `width <= w`

Но сравнение идёт не на всех строках, а поверх уже замороженной базы:

- `A @ 7.5%`

Смысл такой:

- quantile-слой не должен заново заменять базовый ranking;
- он должен быть вторым слоем уверенности поверх уже хороших сделок.

---

## 10. Success Criteria

Новый подэтап считается удачным только если выполняются все три условия:

1. новый трек не ломает текущую силу `entry_path_v1`
2. после conformal и frozen rule он реально улучшает текущую базу `A @ 7.5%`
3. улучшение держится не только по отдельным сделкам, но и в последовательной проверке

Если этого нет, этап считается полезным исследованием, но не новым baseline.

---

## 11. Main Risks

### 11.1. Quantile-головы тянут backbone в плохую сторону

Это главный риск. Его нужно контролировать через mixed checkpoint selection и умеренный вес quantile-loss.

### 11.2. Интервалы снова окажутся слишком широкими

Даже внутри сильной модели quantile-часть может попытаться “спрятаться” в широких границах. Поэтому width обязательно остаётся в validation-метриках.

### 11.3. Гибрид станет слишком сложным для чтения

Чтобы этого не было, новый task и новая модель должны жить в своих файлах, а не раздувать старый `entry_path_v1`.

---

## 12. Expected Outcome

После этапа должно стать ясно одно из двух:

1. quantile-головы действительно усиливают уже рабочий `entry_path_v1`, и тогда проект получает новый confidence-layer поверх базы;
2. даже рядом с сильным backbone quantile-границы не помогают, и тогда эту линию можно честно закрыть без дальнейших итераций на внешних фильтрах.

Оба исхода полезны. Но основной ожидаемый результат этапа — проверить, можно ли получить рабочие нижнюю и верхнюю границу, не теряя уже подтверждённый ranking сигналов.
