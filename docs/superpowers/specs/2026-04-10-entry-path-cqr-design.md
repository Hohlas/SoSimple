# Entry Path CQR v1 — Design Spec

> **Date**: 2026-04-10
> **Status**: Draft
> **Track**: Табличный `CQR` поверх готовых `entry_path_v1` выгрузок
> **Goal**: Проверить, может ли `CQR` дать рабочий слой `trade / no-trade` поверх замороженного `A @ 7.5%`, если текущий adaptive conformal не помогает из-за плохой абсолютной шкалы `ret_24`

---

## 1. Context

Для `entry_path_v1` уже есть замороженная база:

- winner: `A`
- target coverage: `7.5%`
- validation: `36 trades`, `PF=2.67`
- test: `44 trades`, `PF=4.29`

Поверх этой базы уже были проверены два шага:

1. простой `split conformal`;
2. более сильный adaptive conformal с отдельной моделью ошибки.

Оба шага не улучшили базу.

Главный найденный факт:

- после базового отбора `A @ 7.5%` все выбранные сделки на `validation` и `test` имеют `pred_ret_24_dir_atr < 0`;
- то есть модель умеет ранжировать сделки, но плохо держит абсолютный уровень прогноза в шкале `ret_24`;
- из-за этого правило вида `LB > 0` почти обречено даже при более умной калибровке ошибки.

Отсюда новый следующий шаг:

- не пытаться ещё раз оценивать ошибку вокруг старого точечного прогноза;
- вместо этого построить нижнюю и верхнюю границы для самого `true_ret_24_dir_atr` через табличный `CQR`.

---

## 2. Main Idea

`Entry Path CQR v1` строится только на уже готовых табличных выгрузках:

- `entry_path_v1_train_predictions.csv`
- `entry_path_v1_validation_predictions.csv`
- `entry_path_test_predictions.csv`

На `train` активных строках учатся две `LightGBM` quantile-модели:

- нижний квантиль `0.1`
- верхний квантиль `0.9`

Их цель:

- `true_ret_24_dir_atr`

Потом на `validation`:

1. для каждой строки считаются `lower_pred` и `upper_pred`;
2. по ним строится conformal-поправка в стиле `CQR`;
3. получается скорректированный интервал:

```text
LB = lower_pred - q
UB = upper_pred + q
width = UB - LB
```

После этого поверх замороженной базы `A @ 7.5%` сравниваются правила по нижней границе и ширине интервала.

Победитель выбирается только на `validation`, а на `test` применяется уже без перенастройки.

---

## 3. Scope

### Входит в этап

- табличные quantile-модели для `true_ret_24_dir_atr`
- conformal-коррекция quantile-границ на `validation`
- применение только поверх замороженного `A @ 7.5%`
- сравнение базы и небольшого набора `LB/width`-правил
- выбор победителя только на `validation`
- финальная проверка на `test`
- обязательная последовательная проверка

### Не входит в этап

- новый retrain `entry_path_v1`
- изменение основной нейросети
- новый trade filter вместо `A @ 7.5%`
- MT4-интеграция
- размер позиции
- перенос `CQR` в отдельный runtime-слой

---

## 4. Design Principles

### 4.1. Сначала быстрый табличный слой

Это не новый основной ML-трек, а короткий и сильный проверочный подэтап поверх уже готовых выгрузок `entry_path_v1`.

### 4.2. Бить в уровень прогноза, а не в остаток

Новая модель должна предсказывать границы самого `true_ret_24_dir_atr`, а не только ошибку вокруг старого `pred_ret_24_dir_atr`.

Причина:

- текущий блокер именно в плохой абсолютной шкале прогноза;
- если учить только остаток, можно снова сохранить неверный базовый уровень.

### 4.3. Честный split

Схема должна оставаться чистой:

- `train` — обучение двух quantile-моделей;
- `validation` — conformal-калибровка и выбор правила;
- `test` — только финальная проверка.

### 4.4. Только поверх уже выбранной базы

`CQR` здесь не заменяет baseline `A @ 7.5%`, а работает как второй фильтр после него.

### 4.5. Не жертвовать последовательной проверкой

Если кандидат улучшает отдельные сделки, но портит последовательную проверку, он не считается годным.

## 5. Data and Features

### 5.1. Источник данных

Используются уже готовые выгрузки `entry_path_v1`:

- `train`
- `validation`
- `test`

### 5.2. Строки для обучения

Две quantile-модели учатся на всех активных строках `train`, где:

- `signal != 0`

Причина:

- данных больше;
- модель уровня будет устойчивее;
- применение всё равно ограничивается базой `A @ 7.5%`.

### 5.3. Признаки

Используется тот же набор, что уже собран для adaptive-слоя:

- `pred_fav_6_atr`
- `pred_adv_6_atr`
- `pred_fav_12_atr`
- `pred_adv_12_atr`
- `pred_fav_24_atr`
- `pred_adv_24_atr`
- `pred_path_6_prob_neg`
- `pred_path_6_prob_flat`

### 5.4. Целевая величина

Обе quantile-модели предсказывают:

- `true_ret_24_dir_atr`

## 6. Quantile Models

Используются две отдельные `LightGBMRegressor`-модели с `objective='quantile'`:

- `lower_q_model`, квантиль `0.1`
- `upper_q_model`, квантиль `0.9`

Для первого `v1` не сравниваются другие пары квантилей.

Причина выбора `0.1 / 0.9`:

- это достаточно устойчивый первый диапазон;
- при текущих объёмах данных он менее шумный, чем более крайние пары;
- этого достаточно, чтобы проверить саму идею `CQR`.

---

## 7. CQR Calibration

### 7.1. Применение базы

На `validation` и `test` `CQR` применяется только к строкам, которые уже прошли замороженное правило `A @ 7.5%`.

### 7.2. Сырые quantile-границы

Для каждой такой строки считаются:

```text
lower_pred
upper_pred
```

### 7.3. Conformal score

На `validation` считается:

```text
score = max(lower_pred - y_true, y_true - upper_pred)
```

### 7.4. Поправка

По этим `score` берётся conformal-квантиль `q` с finite-sample correction.

После этого строится скорректированный интервал:

```text
LB = lower_pred - q
UB = upper_pred + q
width = UB - LB
```

Это и есть рабочий интервал `CQR v1`.

---

## 8. Candidate Rules

Для первого `v1` сравниваются:

- база без `CQR`
- `LB > 0`
- `LB > 0.25`
- `LB > 0.5`
- `LB > 0 | width <= 1.0`
- `LB > 0 | width <= 1.5`
- `LB > 0.25 | width <= 1.0`
- `LB > 0.25 | width <= 1.5`
- `LB > 0.5 | width <= 1.0`
- `LB > 0.5 | width <= 1.5`

Где:

- `LB` измеряется в ATR-шкале `ret_24`
- `width` — ширина скорректированного интервала

Для первого шага сетка остаётся маленькой, чтобы не раздувать объём и не ловить случайный победитель из-за перебора.

---

## 9. Selection Rules

Победитель выбирается только на `validation`.

Кандидат считается допустимым, только если:

1. после фильтра осталось не меньше `25` сделок;
2. последовательная проверка не хуже базы `A @ 7.5%`;
3. правило не использует `test` при выборе.

Если допустимых кандидатов несколько, приоритет такой:

1. выше `PF` по сделкам по отдельности;
2. при равенстве выше `mean_pnl_atr`;
3. потом выше устойчивость по периодам;
4. потом больше число сделок.

Если ни один `CQR`-кандидат не проходит ограничения, победителем остаётся база.

---

## 10. Evaluation Protocol

### 10.1. Основная проверка

Главная проверка идёт по сделкам по отдельности.

Ключевые метрики:

- `trades`
- `PF`
- `win_rate`
- `mean_pnl_atr`

### 10.2. Проверка по периодам

Используется тот же принцип устойчивости по периодам, что уже принят в trade-filter этапе.

### 10.3. Последовательная проверка

Для каждого кандидата обязательно считается последовательная проверка с тем же горизонтом удержания:

- `24` бара

Она не главный критерий ранжирования, но жёсткий фильтр годности:

- если её `PF` хуже базы, кандидат выбывает.

### 10.4. Test

На `test`:

- не выбирается новый winner;
- не подбирается новая поправка;
- применяется уже замороженное validation-правило.

## 12. Expected Outcome

Этот подэтап должен дать один из двух честных результатов:

1. табличный `CQR` впервые даёт рабочий кандидат поверх `A @ 7.5%`, где `LB > 0` или `LB > m` начинает иметь смысл;
2. даже `CQR` на текущих табличных признаках не спасает слой `trade / no-trade`, и тогда следующий шаг уже должен идти не в новые пост-слои, а в новый модельный трек.

В обоих случаях результат полезен:

- либо появляется рабочий `CQR`-слой;
- либо закрывается вопрос, что проблема глубже текущих табличных надстроек.
