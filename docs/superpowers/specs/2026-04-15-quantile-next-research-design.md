# Quantile Next Research — Design Spec

> **Date**: 2026-04-15
> **Status**: Draft
> **Track**: Следующие research-вопросы после закрытия initial PF-uplift candidates
> **Goal**: Формализовать два следующих направления исследования после провала strict validation-first проверки для `early_timeout`, `NY session exclusion` и `pred_adv12 <= Q75`

---

## 1. Context

К 2026-04-15 закрыты три кандидата из shortlist `PF Uplift Discovery — Beyond ML Layer`:

- `early_timeout_hold_bars=12` — rejected
- `NY session exclusion` поверх frozen `entry_path_v1_quantile` — rejected
- `pred_adv12 <= Q75(validation)` поверх frozen `entry_path_v1_quantile` — rejected

Причины отказа различаются, но общий вывод один:

- найденные uplift-идеи выглядели сильно на historical test;
- при строгой validation-first проверке они не дали достаточного подтверждения для productization.

Из этого следует важный сдвиг:

- дальше не стоит продолжать ещё один узкий filter search поверх уже очень редкого `quantile` baseline в том же формате;
- разумнее проверить две более содержательные гипотезы, которые прямо следуют из уже увиденных данных.

Эти гипотезы и есть предмет текущей спецификации.

---

## 2. Main Idea

Следующий research должен быть разделён на два независимых трека:

1. **Standalone Session System**
   Проверить, является ли session-based фильтрация не дополнением к `quantile`, а самостоятельной торговой системой со своей собственной опорой по сделкам.

2. **Relaxed Baseline Composition**
   Ослабить базовый входной режим так, чтобы получить больше сделок, и только потом проверить, возвращает ли один простой execution/filter-layer прежнее качество без потери support.

Это разные вопросы.

Первый отвечает:

- есть ли в session effect самостоятельный edge, а не только красивое улучшение редкой подвыборки.

Второй отвечает:

- не был ли исходный failure вызван тем, что `quantile` уже слишком селективен и почти не оставляет пространства для дополнительной фильтрации.

---

## 3. Why These Two Tracks

После закрытия NY-session candidate стало ясно:

- improvement был большим по PF;
- но `N` упал ниже порога только потому, что `quantile` уже сам по себе очень редкий.

Это допускает два разных объяснения:

### 3.1. Explanation A

Session effect действительно несёт сильный edge, но поверх `quantile` остаётся слишком мало сделок.

Тогда нужно проверять session logic как отдельную систему, а не как add-on к `quantile`.

### 3.2. Explanation B

Session effect полезен не сам по себе, а как второй слой отбора, если первый слой сделать чуть шире.

Тогда нужно не выбрасывать идею, а сменить базовую конструкцию:

- сначала более широкий baseline;
- потом один простой filter-layer;
- затем strict validation-first verdict.

Обе гипотезы правдоподобны.
Ни одна пока не доказана.

---

## 4. Scope Decomposition

Этот документ фиксирует сразу два research-трека, но **не объединяет их в один implementation plan**.

Причина:

- они отвечают на разные вопросы;
- у них разная базовая архитектура;
- их нужно планировать и реализовывать отдельно.

Следовательно:

- для каждого трека позже должен быть свой отдельный implementation plan;
- результаты должны сравниваться между собой только после завершения обоих треков.

---

## 5. Track A — Standalone Session System

### 5.1. Research Question

Можно ли превратить session-based отбор в самостоятельную торговую систему с достаточным числом сделок и устойчивым качеством, без опоры на frozen `quantile`?

### 5.2. Core Hypothesis

Идея состоит в том, что временная структура рынка может быть не вторичным улучшателем, а первичным источником edge.

В частности, текущий результат по `NY session exclusion` допускает, что:

- проблема была не в самой session logic;
- проблема была в слишком маленьком support после пересечения с `quantile`.

### 5.3. In Scope

В этом треке допустимы:

- standalone benchmark без зависимости от quantile-selected universe;
- один простой session-based rule family;
- validation-first selection;
- frozen test check;
- yearly или иная крупная временная разбивка;
- сравнение с простым baseline того же standalone universe.

### 5.4. Out of Scope

В этот трек не входят:

- composition с несколькими фильтрами сразу;
- повторный search по множеству ML-фич;
- переобучение модели;
- MT4 productization до честного Python verdict;
- свободный перебор многих session windows без явной дисциплины выбора.

### 5.5. Design Principle

Standalone session system должна быть простой и объяснимой.

Хороший вариант:

- один тип session-rule;
- фиксированная временная логика;
- минимальное число степеней свободы.

Плохой вариант:

- набор из многих time windows;
- отдельные исключения для разных месяцев;
- логика, которая объясняется только тем, что она красиво сработала на test.

### 5.6. Success Signals

Трек можно считать успешным, если standalone session system:

- проходит минимальный порог по `N`;
- даёт рабочий `PF`;
- не разваливается по крупным временным срезам;
- остаётся достаточно простой для последующего MT4 parity этапа.

### 5.7. Failure Signals

Трек считается неуспешным, если:

- edge держится только на узком окне настройки;
- `N` снова недостаточен уже в standalone-режиме;
- test резко расходится с validation;
- система требует слишком много условностей, чтобы остаться рабочей.

### 5.8. Expected Deliverable

Итог Track A должен дать один из двух честных выводов:

- `standalone_session_candidate`
- или `reject_session_as_primary_system`

---

## 6. Track B — Relaxed Baseline Composition

### 6.1. Research Question

Если слегка ослабить базовый входной режим и тем самым поднять число сделок, сможет ли один простой filter-layer вернуть или улучшить качество без потери устойчивости?

### 6.2. Core Hypothesis

Текущий frozen `quantile` может быть слишком селективным для второго слоя.

То есть failure некоторых candidate-фильтров мог означать не то, что фильтры бесполезны, а то, что:

- baseline уже забрал только самые редкие сделки;
- любая дополнительная фильтрация сразу опускает support ниже рабочего уровня.

Тогда правильный следующий вопрос:

- существует ли немного более широкий baseline,
- который сам по себе чуть слабее по PF,
- но в композиции с одним простым filter-layer даёт более рабочий итоговый баланс `PF × N`.

### 6.3. In Scope

В этом треке допустимы:

- ограниченный поиск более широкого baseline family;
- выбор baseline только на validation;
- затем проверка только одного дополнительного слоя фильтрации за прогон;
- сравнение с relaxed baseline и с текущим frozen quantile;
- строгий frozen test check после validation selection.

### 6.4. Out of Scope

В этот трек не входят:

- полный новый signal search;
- большие ансамбли фильтров;
- одновременная оптимизация baseline и нескольких filters на test;
- переобучение модели;
- productization до завершения честного benchmark verdict.

### 6.5. Design Principle

Этот трек должен быть построен как двухшаговая система:

1. выбрать один чуть более широкий baseline;
2. проверить поверх него один простой filter-layer.

Нельзя одновременно искать:

- новый baseline;
- лучший session filter;
- лучший adverse filter;
- лучший timeout rule;
- лучшую композицию между ними.

Иначе это быстро превращается в неуправляемый search space.

### 6.6. Comparison Principle

Каждый результат должен сравниваться сразу с двумя базами:

- relaxed baseline без фильтра;
- текущий frozen `entry_path_v1_quantile`.

Это важно, потому что composition может выглядеть хорошо относительно relaxed baseline, но быть всё равно хуже текущего production-like режима.

### 6.7. Success Signals

Трек можно считать успешным, если найденная composition:

- улучшает relaxed baseline по практическому качеству;
- остаётся с достаточным `N`;
- не выглядит хуже frozen quantile по итоговому trade-off;
- сохраняет простую и воспроизводимую логику.

### 6.8. Failure Signals

Трек считается неуспешным, если:

- улучшение держится только в одной точке настройки;
- composition оказывается хуже frozen quantile;
- support снова проваливается ниже рабочего минимума;
- итоговая система становится слишком сложной относительно выгоды.

### 6.9. Expected Deliverable

Итог Track B должен дать один из двух честных выводов:

- `relaxed_composition_candidate`
- или `reject_relaxed_composition`

---

## 7. Shared Validation Discipline

Оба трека должны подчиняться одной и той же дисциплине:

- поиск и выбор делаются только на `validation`;
- `test` используется только как frozen check;
- после одного формального verdict-stage нельзя пересматривать winner по результату `test`.

Это особенно важно здесь, потому что обе идеи возникли после нескольких уже не прошедших uplift-кандидатов.
Значит, риск повторного переобучения на историческом test уже повышен.

---

## 8. Shared Evaluation Metrics

Для обоих треков должны считаться:

- `trades`
- `PF`
- `win_rate`
- `mean_pnl_atr`
- крупные временные срезы

Если используется composition-трек, дополнительно нужен ещё один вопрос:

- насколько новый режим реально лучше текущего frozen `quantile`, а не только своего промежуточного baseline.

---

## 9. Priority Order

Рекомендуемый порядок исследований:

1. **Track A: Standalone Session System**
2. **Track B: Relaxed Baseline Composition**

Причина такого порядка:

- Track A проще концептуально;
- он быстрее даёт ответ, существует ли вообще самостоятельный session edge;
- если Track A провалится полностью, это сузит пространство Track B и заставит осторожнее относиться к session-based composition;
- если Track A даст умеренно живой результат, Track B можно будет строить уже на более понятной логике.

---

## 10. Decision Rule

После выполнения обоих треков должен быть дан простой ответ:

Какой следующий research-путь рациональнее после закрытия initial PF-uplift shortlist?

Возможны три честных исхода:

- standalone session system заслуживает отдельного продолжения;
- relaxed baseline composition заслуживает отдельного продолжения;
- обе идеи не дают достаточного подтверждения, и проекту нужен другой research-вектор.

---

## 11. Next-Step Output

Этот design-док не запускает реализацию напрямую.

Он должен быть использован как вход для двух отдельных следующих документов:

- отдельного implementation plan для Track A;
- отдельного implementation plan для Track B.

То есть следующий чат должен начинаться не с кода, а с выбора, какой из двух треков планировать первым.
