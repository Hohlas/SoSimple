# Next Research Design — Higher-Frequency Trading Systems

> **Date**: 2026-04-15
> **Status**: Draft
> **Track**: Следующий research после фиксации того, что текущий самый сильный режим слишком редкий для практической торговли
> **Goal**: Построить более частые торговые системы на базе `entry_path`, сохранив рабочую прибыльность и устойчивость по времени

---

## 1. Context

К 2026-04-15 в проекте уже зафиксированы два важных факта:

1. Текущий самый сильный слой отбора (`entry_path_v1_quantile`) даёт хорошую прибыльность, но слишком малое число сделок для комфортной и быстрой практической проверки.
2. Несколько попыток улучшить этот редкий режим дополнительными фильтрами не дали честного productization-результата.

Также в истории проекта уже были две важные линии, на которые нужно опираться, а не повторять их вслепую:

- **`entry_path_v1` как более широкая база** — уже давал больше сделок, чем текущий самый строгий режим;
- **outcome-aligned retraining** — уже пытался учить модель на более прямую торговую цель, но провалился из-за слабой постановки target-меток.

Из этого следует практический сдвиг:

- временно убрать приоритет с очень строгих фильтров;
- перейти к поиску более частой системы;
- проверять два разных research-вектора отдельно;
- использовать проверку на близких инструментах только как финальную проверку доверия, а не как часть подбора.

---

## 2. Main Research Question

Главный вопрос следующего этапа:

Можно ли получить торговую систему с частотой порядка `40–50` сделок в год на основном инструменте, сохранив `PF > 2` и достаточную устойчивость по времени?

Этот вопрос делится на два независимых research-трека:

1. **Более частая версия текущего `entry_path`**
2. **Прямая модель “торговать / не торговать”**

Эти треки нельзя смешивать в один implementation plan, потому что:

- они отвечают на разные вопросы;
- у них разная постановка задачи;
- их нужно оценивать раздельно;
- иначе станет невозможно честно понять, откуда именно появился результат.

---

## 3. Shared Principles

### 3.1. Main Instrument First

Все решения о качестве системы принимаются только на основном инструменте.

Проверка на близких инструментах:

- не используется для выбора модели;
- не используется для подбора признаков;
- не используется для настройки порогов;
- применяется только к системам, уже близким к production.

### 3.2. No Artificial Position Constraints

Ограничения вида:

- “только одна открытая позиция”
- “нельзя одновременно входить в разные стороны”

в research-дизайн не включаются, потому что:

- они не противоречат торговой платформе;
- они не противоречат торговым принципам пользователя;
- искусственное введение таких ограничений исказит результат относительно реальной практики.

Но одно правило обязательно:

- одинаковые торговые допущения должны применяться ко всем сравниваемым системам.

### 3.3. Keep No-Trade Rows

Строки без сделки не должны полностью удаляться из обучения.

Причина:

- модели нужно видеть не только хорошие сделки;
- модели нужно понимать, где **не надо** торговать.

Правильная задача не в удалении таких строк, а в том, чтобы:

- они не подавляли сигнал полезных торговых ситуаций;
- схема обучения правильно балансировала “торговать” и “не торговать”.

### 3.4. Validation-First Discipline

Для обоих треков обязателен один и тот же порядок:

- поиск и выбор делаются на `validation`;
- `test` используется только как frozen check;
- близкие инструменты проверяются только после успеха на основном инструменте.

---

## 4. Shared Evaluation Standard

### 4.1. Core Metrics

Для обоих треков обязательно считать:

- `trades_total`
- `trades_per_year`
- `PF`
- `win_rate`
- `mean_pnl_atr`
- `drawdown`
- `ulcer_index`

### 4.2. Stability Metrics

Помимо обычной прибыльности нужно отдельно оценивать временную устойчивость:

- число слабых периодов;
- наличие отрицательных годовых или квартальных срезов;
- концентрацию прибыли по времени;
- концентрацию прибыли в нескольких лучших сделках.

В этом дизайне это фиксируется как отдельная группа требований:

- **profit concentration** — слишком большая доля прибыли не должна приходиться на top-10% сделок;
- **time concentration** — результат не должен зависеть почти полностью от одного короткого участка истории;
- **equity smoothness** — рост капитала должен быть достаточно ровным, без слишком рваной формы.

### 4.3. Practical Target

Целевой практический ориентир для системы, близкой к production:

- `40–50` сделок в год;
- `PF > 2`;
- отсутствие явного развала по периодам;
- прибыль не сосредоточена в нескольких всплесках.

`PF > 3` считается отличным, но не обязательным требованием.

---

## 5. Track A — Higher-Frequency Entry Path

### 5.1. Research Question

Можно ли сделать более частую версию текущего `entry_path`, не ломая основную идею трека и не сводя всё к очередному очень строгому фильтру?

### 5.2. Core Hypothesis

Текущий `entry_path` может быть улучшен так, чтобы:

- давать больше сделок;
- сохранять рабочий уровень прибыльности;
- оставаться основой для более позднего слоя повышения надёжности.

### 5.3. In Scope

В этот трек входят:

- новые признаки для датасета;
- новая схема обучения;
- пересмотр весов и важности разных типов строк;
- новые варианты слоя отбора сделок внутри логики `entry_path`;
- ранняя фильтрация признаков через Mutual Information;
- поздний разбор сильных кандидатов через SHAP.

### 5.4. Out of Scope

В этот трек не входят:

- возврат к сверхредкому режиму как главной цели;
- использование проверки на близких инструментах для подбора;
- применение Conformal Prediction на раннем этапе;
- бесконечный цикл “чистим признаки и переобучаем” после каждого слабого улучшения.

### 5.5. Design Principle

Этот трек должен отвечать на вопрос:

Можно ли сделать `entry_path` practically usable по частоте, а не только сильным по качеству на редких сделках?

Поэтому приоритеты здесь такие:

1. увеличить число сделок;
2. сохранить `PF > 2`;
3. не потерять устойчивость по времени;
4. не прятать проблему частоты за очень жёстким поздним фильтром.

### 5.6. Success Signals

Трек можно считать успешным, если найден кандидат, который:

- даёт заметно больше сделок, чем текущий редкий режим;
- движется к диапазону `40–50` сделок в год;
- сохраняет `PF > 2`;
- не разваливается по годам или кварталам;
- не держится на нескольких аномально сильных сделках.

### 5.7. Failure Signals

Трек считается неуспешным, если:

- рост частоты достигается ценой слишком сильного падения `PF`;
- прибыль оказывается сосредоточенной в нескольких сделках;
- рост результата виден только на одном коротком участке истории;
- улучшение возможно только после возвращения к очень редкому строгому отбору.

---

## 6. Track B — Direct Trade/No-Trade Model

### 6.1. Research Question

Лучше ли учить модель сразу принимать торговое решение, чем сначала предсказывать свойства движения цены, а затем строить отдельный слой отбора?

### 6.2. Core Hypothesis

Текущая постановка задачи может быть слишком косвенной.

Возможно, модель даст более частую и practically useful систему, если её целевая задача будет ближе к прямому торговому вопросу:

- торговать;
- не торговать;
- при необходимости, отдельно учитывать направление.

### 6.3. Important Historical Constraint

Похожая линия уже была исследована как outcome-aligned retraining и была закрыта.

Следовательно, этот новый трек допустим только как **новая постановка**, а не как повтор старой.

Запрещено повторять:

- старые target-метки, слишком далёкие от реального торгового решения;
- прежнюю слабую логику “label close-to-close через фиксированное число баров” как единственный смысл сделки.

### 6.4. In Scope

В этот трек входят:

- новая целевая переменная;
- новая схема обучения;
- новая логика оценки качества именно как торгового решения;
- сравнение с Track A по единым критериям качества.

### 6.5. Out of Scope

В этот трек не входят:

- буквальное повторение старого outcome-aligned этапа;
- подбор через близкие инструменты;
- раннее использование Conformal Prediction;
- искусственное обнуление строк “не торговать”.

### 6.6. Design Principle

Этот трек должен отвечать на вопрос:

Можно ли получить более частую систему, если модель сразу учится решать торговую задачу, а не описывать рынок косвенно?

Главный риск здесь не в архитектуре модели, а в плохой целевой метке.

Поэтому качество target-definition важнее, чем сложность модели.

### 6.7. Success Signals

Трек можно считать успешным, если новый target family:

- даёт частоту, близкую к целевому диапазону;
- сохраняет `PF > 2`;
- показывает устойчивость по времени;
- не строит весь результат на нескольких выбросах.

### 6.8. Failure Signals

Трек считается неуспешным, если:

- частота есть, но качество системно слабое;
- качество держится только на одном участке истории;
- целевая метка приводит к модели, которая формально выглядит рабочей, но practically не решает торговую задачу.

---

## 7. Role Of Mutual Information

Mutual Information (взаимная информация: мера связи признака с целевой переменной) допустимо использовать как ранний инструмент грубой фильтрации признаков.

Это особенно полезно:

- в Track A перед основной серией обучения;
- в Track B при первичной оценке новых target-меток.

Mutual Information не является самостоятельным proof-of-value:

- он не заменяет обучение модели;
- он не заменяет validation-first benchmark;
- он служит только ранней чистке слишком слабых признаков.

---

## 8. Role Of SHAP

SHAP допустим только как поздний разбор сильных кандидатов.

Правильный цикл такой:

1. найден устойчивый положительный кандидат;
2. через SHAP проверяется, на каких признаках реально стоит модель;
3. при необходимости набор признаков очищается;
4. после этого запускается **один новый полный цикл обучения и проверки**.

SHAP нельзя превращать в бесконечный iterative optimization loop.

---

## 9. Role Of Conformal Prediction

Conformal Prediction (слой оценки надёжности прогноза) не является стартовым инструментом для этих двух треков.

Его роль допустима только как поздний усилитель уже более частой системы.

Практический сценарий для возврата к нему:

- базовая система уже даёт большой запас сделок, например `N > 100`;
- базовая прибыльность умеренно положительна, например `PF > 1.5`;
- прибыль распределена достаточно ровно по времени;
- после этого Conformal Prediction проверяется как способ уменьшить `N` и поднять `PF`.

Типичный desirable outcome:

- база: частая, умеренно сильная;
- после слоя надёжности: меньше сделок, но всё ещё `N > 40` и уже более высокий `PF`.

Conformal Prediction не должен использоваться как способ “спасти” слишком редкую систему.

---

## 10. Cross-Instrument Check

Проверка на близких инструментах допустима только как финальный этап доверия.

Она применяется только к системам, которые уже:

- удовлетворяют требованиям качества на основном инструменте;
- близки к production decision.

Проверка на близких инструментах:

- не участвует в выборе признаков;
- не участвует в выборе target-меток;
- не участвует в выборе порогов;
- не используется как часть optimization loop.

---

## 11. Priority Order

Рекомендуемый порядок такой:

1. Track A — более частый `entry_path`
2. Track B — прямая модель “торговать / не торговать”
3. Mutual Information как ранний фильтр признаков
4. SHAP только для сильных кандидатов
5. Conformal Prediction только после появления частой системы с запасом сделок
6. Cross-instrument check только для near-production кандидатов

Track A идёт первым, потому что:

- он ближе к уже работающему контуру;
- у него меньше методический риск;
- он напрямую продолжает уже подтверждённую линию `entry_path_v1`.

Track B идёт отдельно, а не как продолжение Track A, потому что:

- это уже другая учебная постановка;
- смешивать их в один план нельзя.

---

## 12. Decision Rule

После завершения обоих треков должен быть дан простой ответ:

Какой research-путь даёт более частую, practically useful и устойчивую систему на основном инструменте?

Возможны только три честных исхода:

- выигрывает Track A;
- выигрывает Track B;
- оба трека не дают достаточного результата и требуют нового research-поворота.

---

## 13. Expected Deliverables

Этот design-док должен привести к двум отдельным следующим документам:

- отдельному implementation plan для **Track A — Higher-Frequency Entry Path**
- отдельному implementation plan для **Track B — Direct Trade/No-Trade Model**

Каждый план должен:

- использовать общую систему метрик;
- держать validation-first дисциплину;
- не использовать близкие инструменты для выбора;
- отдельно фиксировать, как учитывается устойчивость по времени и концентрация прибыли.
