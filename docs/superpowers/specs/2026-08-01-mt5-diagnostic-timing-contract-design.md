# MT5 Diagnostic Timing Contract Design

Дата: 2026-08-01
Статус: DESIGN (до реализации)
Тип: методическое улучшение диагностического контура, не новый winner-поиск.

## Цель

Сделать временной контракт MT5 diagnostic loop проверяемым и моделируемым:

1. Заполнять `feature_time`, `feature_available_time`, `decision_time` честными
   значениями вместо копирования `signal_time` во все поля.
2. Проверять инвариант порядка событий в рантайме и фиксировать его в
   артефактах (`events.csv`).
3. Дать возможность симулировать латентность решения модели (задержку между
   доступностью признаков и фактическим размещением ордера).

Результат остаётся `DIAGNOSTIC_ONLY`. `locked_test` не открывать. Новых
PnL/PF-заявлений этап не делает.

## Почему нужен

Отчёт `docs/reports/2026-07-31-mt5-batch-selection.md` фиксирует ограничение
(Limitations п. 6):

> bridge копирует `signal_time` во все временные поля (diagnostic). Не является
> доказательством leakage-free.

То же самое зафиксировано в плане `docs/superpowers/plans/2026-07-31-mt5-batch-selection.md`
(Known Risks: «Timing contract тривиален»).

Проблема не в том, что существует утечка данных: проверка показывает, что
механика исполнения уже корректна (см. Установленные факты). Проблема в том,
что артефакты (файлы сигналов, события) **не позволяют проверить** порядок
событий. Контракт выполняется «по конструкции» эксперта, а не по данным.
Любая будущая правка эксперта или моста может молча сломать этот порядок без
обнаружения.

Дополнительно: три времени сейчас неразличимы, поэтому нельзя моделировать
реальную задержку между доступностью признаков и решением модели — это мешает
приблизить тест к живой торговле.

## Установленные факты (проверено по коду и артефактам)

1. **Размещение уже на следующем баре.** В `MT/MQL5/Experts/$o$imple.mq5:83`
   переменная `bar` зафиксирована как `1` и нигде не меняется. Советник
   матчит сигнал через `MT5_FindEntrySignal(Time[bar])` = `Time[1]` — начало
   последнего закрытого бара (`MT/MQL5/Include/lib_ML_Signal.mqh:665`).
   Размещение происходит на первом тике следующего бара. Подтверждение из
   событий top-кандидата:

   ```text
   signal_time=2021.01.05 07:00 -> ORDER_PLACED@2021.01.05 08:00
   signal_time=2021.01.07 05:00 -> ORDER_PLACED@2021.01.07 06:00
   ```

   Это совпадает с Python-контрактом «первый бар строго после signal_time»
   (`_first_eligible_index(..., side="right")`, `ML/baseline/benchmark_fractal0_entry_exit_grid.py:337-340`).

2. **Лимитная цена не из будущего.** Эмпирически `calculation_open` в
   `ML/reports/fractal0_entry_quality_filter_scores.csv` = open бара,
   следующего за `signal_time`. Ордер ставится на открытии этого же бара,
   когда его open уже известен.

3. **Признаки batch-профилей не используют будущее.** Профили
   `time_plus_atr` и `simple_combined` состоят из ATR, календарных признаков,
   pre-entry дистанции до fractal0 и плотности фракталов — все помечены
   `available_at_decision_time: True`
   (`ML/baseline/benchmark_entry_based_amplitude_movement.py:497-570`).

4. **Мост склеивает времена.** `ML/baseline/prepare_mt5_entry_source.py:66-67`
   требует `time == signal_time` и штампует все три поля одной меткой
   (строки 74-86).

5. **OR-матчинг создаст двойной матч при расхождении полей.**
   `MT5_FindEntrySignal` (строка 130) матчит `decision_time == barTime ИЛИ
   entry_time == barTime`. Пока оба равны — совпадение одно. Как только
   `decision_time` разойдётся с ключом матчинга, сигнал будет находиться
   дважды → на втором проходе появятся лишние `OPEN_FAILED
   position_or_pending_order_exists`.

Вывод: существующей утечки в исполнении нет; задача — перевести контракт из
«по конструкции» в «проверяемо и моделируемо».

## Контракт времени (Decision Time)

Каждому сигналу в файле входа соответствует последовательность моментов:

| Поле | Значение | Смысл |
|---|---|---|
| `feature_time` | T (сигнальный бар) | последний бар, чьи данные (close[T], fractal0) использованы моделью |
| `time` (ключ матчинга эксперта) | T | база для размещения: эксперт ставит ордер на открытии бара T+1 |
| `feature_available_time` | T+1 | к моменту открытия бара T+1 бар T уже закрыт, признаки стали доступны |
| `decision_time` | T+1 | момент, когда модель посчитала скор |
| фактическое время `ORDER_PLACED` | open[T+1] | момент размещения (пишет эксперт, TimeCurrent) |

Инвариант для каждого сигнала:

```text
feature_time <= time < feature_available_time <= decision_time <= время ORDER_PLACED
```

Разрешается только информация, доступная к `feature_available_time`. Запрещено
использование close/OHLC/fractal полей баров позже `feature_time`; любые
future-derived поля (факт fill/no-fill, фактическая fill price, fill lag)
исключены из признаков.

Латентность моделируется опциональным сдвигом: `decision_time = T+1+k`
(k >= 0 баров). Контракт разделяется на два режима:

- `latency_bars=0`: сравнимый диагностический режим. `time=T`,
  `feature_available_time=T+1`, `decision_time=T+1`, размещение остаётся на
  открытии T+1. Этот режим нужен для повторного batch после исправления
  временных полей.
- `latency_bars>0`: отдельный диагностический режим задержки. В этом режиме `time`
  должен быть сдвинут до `decision_time - 1 бар`, чтобы матчинг через
  `Time[1]` приводил к размещению не раньше `decision_time`. Такой прогон
  меняет момент размещения и не сравним напрямую с batch 2026-07-31.

Для текущей реализации по умолчанию используется только `latency_bars=0`.
Поддержка `latency_bars>0` должна быть явно помечена как отдельный
диагностический режим и не участвовать в выборе winner.

## Изменения по файлам

### 1. Мост `ML/baseline/prepare_mt5_entry_source.py`

- Убрать жёсткое требование `time == signal_time` (строки 66-67).
- Вместо штамповки (строки 74-86) заполнять поля по контракту:

  ```python
  "time": signal_time,                      # T, ключ матчинга
  "feature_time": signal_time,              # T
  "feature_available_time": next_bar,       # T+1
  "decision_time": next_bar,                # T+1
  ```

  где `next_bar` = следующий H1 бар после `signal_time`.
- Добавить валидацию `feature_time <= time < feature_available_time <= decision_time`
  для всех строк.
- Обновить метаданные `time_policy` (строка 118): вместо «copied from
  signal_time; diagnostic bridge only» записать описание нового контракта и
  sha256 файла сигналов.

### 2. Экспорт `ML/baseline/export_mt5_entry_signals.py`

Логика построения export-frame продолжает прокидывать четыре временные колонки
как есть. Код метаданных меняется: в `_build_metadata` добавить ключ
`timing_contract` с текстом инварианта и значением `latency_bars` (по умолчанию
0), чтобы артефакт фиксировал контракт.

### 3. Эксперт `MT/MQL5/Include/lib_ML_Signal.mqh`

- **Единый ключ матчинга.** В `MT5_FindEntrySignal` (строка 130) убрать OR:
  матчить только по `MT5_EntryTimes[i] == barTime` (`time` из файла).
  `MT5_DecisionTimes` остаётся чисто описательным полем и в матчинге не
  участвует. Это устраняет риск двойного матча.
- **Проверка на загрузке.** В `MT5_ENTRY_INIT` (строки 410-468) добавить
  валидацию для каждой строки:
  `FeatureTimes[i] <= EntryTimes[i] < FeatureAvailableTimes[i] <= DecisionTimes[i]`.
  При нарушении писать событие `TIMING_VIOLATION` и пропускать сигнал вместо
  тихого размещения.
- **Python-схема событий.** Одновременно добавить `TIMING_VIOLATION` в
  `MT5_EVENT_NAMES` (`ML/baseline/mt5_signal_schema.py`), иначе новый event log
  будет отвергаться валидатором как неизвестное событие.
- Код размещения (строки 665-725) не меняется: механика `Time[1]` и
  размещение на открытии следующего бара остаются прежними.

### 4. Методология `docs/methodology/13b-mt5-execution-parity.md`

После реализации синхронизировать описание diagnostic executor:

- заменить текущую формулировку «строка выбирается по `decision_time` или
  `time`» на единый ключ матчинга `time`;
- расширить timing contract до
  `feature_time <= time < feature_available_time <= decision_time <= execution_time`;
- добавить `TIMING_VIOLATION` в список событий диагностического executor.

Если методология не обновлена в том же изменении, отчёт этапа должен явно
указать временное локальное ужесточение спецификации относительно `13b`.

### 5. Прогон

- Перегенерировать 32 файла сигналов (`run_mt5_batch.py --phase signals`),
  smoke-тест, затем полный batch (resume-by-skip отработает по факту
  изменения файлов сигналов).
- После прогона выполнить проверку инварианта по всем `events.csv` только для
  событий, связанных с сигналом и имеющих непустые timing-поля.

## Верификация / Acceptance

1. Для всех 32 `batch/{run_id}/events.csv` выполняется запрос-проверка для
   строк, связанных с сигналом (`ORDER_PLACED`, `ORDER_EXPIRED`, `OPEN`,
   `OPEN_FAILED`, `ML_EVAL`, `ML_CLOSE`, `CLOSE`) и имеющих непустые
   timing-поля:

   ```text
   для каждой проверяемой строки:
   feature_time <= time < feature_available_time <= decision_time <= время события
   ```

   `TX_OPEN`/`TX_CLOSE` сейчас допускаются с пустыми timing-полями, потому что
   связка выполняется в Python reconciliation; их нельзя включать в эту
   проверку без отдельного обогащения по связанному сигналу.
2. Ни одного события `TIMING_VIOLATION` в логах; Python-валидатор событий
   принимает это имя как известное.
3. Механика размещения для `latency_bars=0` не изменилась: `ORDER_PLACED`
   по-прежнему происходит на открытии бара, следующего за `signal_time`
   (сверка на smoke + top-кандидате).
4. Число `UNEXPLAINED == 0` для всех прогонов (reconciliation не сломан).
5. В отчёте реализации указано, что `docs/methodology/13b-mt5-execution-parity.md`
   синхронизирован с новым единым ключом матчинга, либо явно отмечено временное
   локальное расхождение.

## Альтернативы

1. **Выбрана: минимальное изменение, ключ матчинга = `time`.** Механика
   размещения не трогается, дифф мал, контракт сохраняется.
2. **Размещение по `decision_time` через `Time[0]`.** Чище семантика полей
   (время действия = время решения), но смена `Time[1]` на `Time[0]` в
   торговом коде затрагивает lifecycle-арифметику (`bars_since_fill`,
   `SHIFT(OrderOpenTime()) - bar`) — рискованно и выходит за рамки задачи.
3. **Ничего не делать.** Контракт остаётся «не доказан»; любая будущая правка
   может молча сломать порядок событий.

## Риски и ограничения

- **Не менять момент размещения.** Любой сдвиг сделает результаты несравнимыми
  с batch 2026-07-31. Основная задача — только сделать контракт проверяемым
  при `latency_bars=0`; `latency_bars>0` является отдельным диагностическим
  режимом.
- **Семантика `time` = бар до размещения** (off-by-one из-за `Time[1]` в
  эксперте) неочевидна. Задокументировать в метаданных экспорта и в шапке
  файла сигналов.
- **Спецификация должна быть под контролем git.** Этот файл должен быть добавлен
  в git вместе с планом/реализацией; иначе связанное проектное решение не будет
  воспроизводиться из чистого checkout.
- **Стоимость:** перегенерация 32 файлов + smoke + полный batch (~4.5 часа).
- **`max_fill_lag_bars`** остаётся 6 (`run_mt5_batch.py:140`); контракт не
  влияет на окно ожидания исполнения.
- Статус результата не выше `DIAGNOSTIC_ONLY`; PnL/PF-выводы запрещены без
  cost model, split disclosure и locked-test protocol.

## Вне объёма

- Корректность самих признаков моделей (проверена отдельно в
