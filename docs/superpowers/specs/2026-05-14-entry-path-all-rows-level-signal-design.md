# Entry Path All-Rows Level Signal Design

> **Date**: 2026-05-14
> **Status**: Draft
> **Track**: Entry path candidate-source audit
> **Goal**: Спроектировать live-safe правило `signal_candidate` по всей строке фракталов, где направление сделки берётся только из `fractal0.direction`, а старая модель используется только как фильтр через старый threshold.
> **Related materials**: `docs/reports/2026-05-14-entry-path-all-rows-ranking.md`, `docs/reports/2026-05-14-entry-path-causal-surrogate.md`, `docs/reports/2026-05-14-entry-path-direct-bar-model.md`, `docs/DATA_FLOW.md`

## Контекст

Текущий `entry_path_v1_live_safe` не использует будущие признаки во входе
модели. Но экспорт торговых сигналов всё ещё зависит от:

```python
selected = (frame["signal"] != 0) & (score >= threshold)
```

В offline `signal` построен через `label_all()` и использует полный исторический
файл. В live raw `Nero.csv` этот `signal` равен нулю. Значит такой `signal`
нельзя считать готовым production-кандидатом сделки.

Первый all-rows benchmark уже показал отрицательный результат: просто убрать
`signal != 0`, взять направление из `fractal0.direction` и применить старый
`pred_ret_24_dir_atr` нельзя. На test PF был ниже 1.

Вывод: нужен не простой all-rows gate, а новый live-safe источник
`signal_candidate`, который отвечает на вопрос:

> находится ли цена `fractal0.price` на сильном уровне?

## Основная идея

Одна строка `Nero.csv` содержит текущую отсортированную строку фракталов:

```text
fractal0, fractal1, ..., fractal99
```

`fractal0` — новый левый фрактал после сортировки. Его собственные поля почти
не описывают силу уровня. Из `fractal0` для торгового решения напрямую берём
только:

- `fractal0.direction` — направление сделки;
- `fractal0.price` — координата уровня, относительно которой анализируется вся
  строка фракталов.

Сила уровня определяется окружением вокруг `fractal0.price`: какие рядом есть
фракталы, как они расположены по цене, какие у них направления, сила, пробои,
историческая реакция цены и возраст.

Новый `signal_candidate` должен строиться по всей строке фракталов. Если
candidate найден, направление сделки задаётся так:

```text
fractal0.direction == -1 -> BUY
fractal0.direction ==  1 -> SELL
```

После этого старый score текущей модели используется только как дополнительный
фильтр:

```python
selected = (signal_candidate != 0) & (score >= original_threshold)
```

`original_threshold` берётся из прошлого frozen rule без нового подбора.

## Термины

**Строка фракталов** — одна строка `Nero.csv` после сортировки `fractal*`.

**Уровень** — область цены вокруг `fractal0.price`, а не точная цена одним
числом.

**Сильный уровень** — уровень, после касания которого с повышенной вероятностью
возникает отскок в сторону сделки.

**Candidate-source** — правило или модель, которая решает, есть ли вообще
кандидат сделки. Это не финальный торговый сигнал.

**Score-фильтр** — старая модельная оценка, например `pred_ret_24_dir_atr`,
которая применяется только после появления candidate.

## Временная корректность

Входные признаки должны быть доступны в текущей строке `Nero.csv`.

Согласно `docs/DATA_FLOW.md`, поля `Up/Dn` внутри `fractal*` формируются в
`lib_PIC.mqh` инкрементально:

- новый уровень создаётся в `NEW_LEVEL()`;
- `LEVELS_FIND_AROUND()` обновляет `Up/Dn` только по уже прошедшим барам;
- `NERO_CSV_CREATE()` записывает в строку только состояние, известное на момент
  этой строки.

Значит `Up/Dn` старых фракталов можно использовать как исторические признаки,
если они уже находятся в текущей строке.

Но будущие `up_3..dn_48` для текущего `fractal0` можно использовать только как
цели обучения, а не как входные признаки.

## Требования

1. Работать только с отсортированной строкой фракталов.
2. Проверить, что offline preprocessing и runtime preprocessing дают одинаковую
   сортировку `fractal0..fractal99`.
3. Направление сделки брать только из `fractal0.direction`.
4. `fractal0.price` использовать только как точку отсчёта для анализа других
   фракталов.
5. `label_all().signal` использовать только как сравнительную метку, но не как
   production-сигнал.
6. Старый score и старый threshold не подбирать заново в первой итерации.
7. Все торговые проверки выполнять теми же метриками, что в предыдущих тестах:
   PF, число сделок, win rate, средний PnL в ATR, годы, sequential test.

## Нецели

В этой спецификации не меняются:

- MT4 execution;
- формат `ml_signals.csv`;
- старый checkpoint `entry_path_v1_live_safe`;
- frozen threshold старого score-фильтра;
- `label_all()` как историческая разметка.

Также это не production approval. Цель этапа — исследовать candidate-source.

## Признаки уровня

### Нормализация относительно `fractal0.price`

Для каждого фрактала `fractali` считаем:

```text
distance_atr = (fractali.price - fractal0.price) / ATR
abs_distance_atr = abs(distance_atr)
```

Так модель не видит абсолютную цену инструмента. Она видит структуру уровня
относительно текущего `fractal0.price`.

### Зоны вокруг уровня

Строятся агрегаты по ценовым зонам:

```text
0.00..0.25 ATR
0.25..0.50 ATR
0.50..1.00 ATR
1.00..2.00 ATR
2.00..4.00 ATR
```

Для каждой зоны считаются:

- количество фракталов;
- количество верхних и нижних фракталов;
- количество same-direction и opposite-direction фракталов относительно
  направления сделки;
- количество `strong`;
- количество пробитых и непробитых;
- сумма и максимум `power`;
- средний и максимум `count`;
- максимум `impulse`;
- сумма исторической реакции `Up/Dn`, если поле уже накоплено в текущей строке.

### Ближайшие фракталы

Дополнительно берутся ближайшие `K` фракталов к `fractal0.price`, например:

```text
K = 8, 16, 32
```

Для каждого ближайшего фрактала сохраняются:

- `distance_atr`;
- `direction`;
- `same_direction`;
- `strong`;
- `break`;
- `reverse`;
- `power`;
- `count`;
- `impulse`;
- `fractal_atr`;
- накопленные `Up/Dn` этого фрактала, если они есть в текущей строке.

### Признаки реакции цены

Для старых фракталов `Up/Dn` считаются исторической реакцией цены на уровень.
Их можно агрегировать по зонам:

- средний и максимальный favorable move;
- средний и максимальный adverse move;
- отношение favorable/adverse;
- число фракталов, где favorable заметно больше adverse.

Для BUY:

```text
favorable = Up
adverse = Dn
```

Для SELL:

```text
favorable = Dn
adverse = Up
```

## Цели обучения

Цели строятся для `fractal0`, но не попадают во вход модели.

Для всех целей используются:

```text
fav_H = движение в сторону сделки за H баров
adv_H = движение против сделки за H баров
```

Для BUY:

```text
fav_H = up_H
adv_H = dn_H
```

Для SELL:

```text
fav_H = dn_H
adv_H = up_H
```

### Target Family A: быстрый отскок

Цель:

```text
adv_6 < N * ATR
fav_6 >= Y * ATR
```

Смысл: за первые 6 часов цена дала сильный ход в сторону сделки и не прошла
против нас дальше стопа.

Проверяемая сетка:

```text
N = 1.5, 2, 3
Y = 2, 3, 4
```

### Target Family B: ступенчатый отскок

Цель:

```text
fav_6  >= 1 * X * ATR
fav_12 >= 2 * X * ATR
fav_24 >= 3 * X * ATR
fav_48 >= 4 * X * ATR
```

Смысл: уровень дал движение, которое развивалось по времени, а не было
одиночным шумовым выбросом.

Проверяемая сетка:

```text
X = 0.5, 0.75, 1.0
```

### Target Family C: отскок с ограниченным риском

Цель:

```text
fav_24 >= X * ATR
adv_12 <= Y * ATR
```

Смысл: уровень дал достаточно большой ход в сторону сделки, но раннее движение
против сделки было ограничено.

Проверяемая сетка:

```text
X = 3, 4, 5
Y = 1.5, 2, 3
```

### Target Family D: trailing-прибыль

Цель:

```text
trailing stop N * ATR закрыл сделку по стопу с профитом >= Z * ATR
```

Смысл: цена достаточно ушла в сторону сделки, стоп подтянулся, затем откат
закрыл сделку в плюс. Это учитывает путь цены, а не только максимум движения.

Проверяемая сетка:

```text
N = 2, 3, 4, 5
Z = 1, 2, 3
horizon = 24, 48
```

Важно: старая цель вида `fav_24 - adv_24 >= X * ATR` не используется как
основная. Она может принять плохую сделку, где цена сначала ушла против нас на
много ATR, а потом восстановилась.

### Target Family E: прогноз величин

Модель предсказывает не один класс, а набор величин:

```text
fav_3, fav_6, fav_12, fav_24, fav_48
adv_3, adv_6, adv_12, adv_24, adv_48
trail_pnl_* для выбранных N/horizon
```

Потом торговое правило строится поверх прогнозов. Например:

```text
pred_fav_24 >= 4 ATR
pred_adv_12 <= 2 ATR
```

Этот путь сложнее, но может лучше использовать связь между горизонтами.

## Подходы к моделированию

### Подход 1: простые правила

Строим признаки уровня и подбираем пороги вручную или через grid search.

Плюсы:

- проще объяснить;
- проще найти ошибку;
- меньше риск переобучения.

Минусы:

- может не увидеть сложные сочетания признаков.

### Подход 2: классификатор сильного уровня

Модель получает признаки уровня и предсказывает вероятность target family:

```text
P(strong_level)
```

Candidate появляется, если:

```text
P(strong_level) >= candidate_threshold
```

Плюсы:

- лучше подходит для сложной структуры уровня;
- можно сравнить разные цели A-D одной и той же процедурой.

Минусы:

- нужно аккуратно выбирать порог на validation;
- нужна проверка важности признаков.

### Подход 3: прогноз величин

Модель предсказывает `fav/adv/trail_pnl`, а затем правило выбирает сделки.

Плюсы:

- наиболее гибкий путь;
- модель не привязана к одному бинарному target.

Минусы:

- сложнее обучение;
- сложнее интерпретация;
- нужен отдельный слой торгового правила.

## Рекомендуемый первый этап

Первым этапом делать не полный neural retrain, а исследовательскую матрицу:

1. Построить live-safe признаки уровня по всей строке фракталов.
2. Проверить Target Families A-D как бинарные цели.
3. Для каждого target обучить простой классификатор.
4. Candidate direction брать только из `fractal0.direction`.
5. Применить старый score:

```python
score >= original_threshold
```

6. Сравнить торговые результаты на validation/test.

Target Family E оставить вторым этапом, если A-D покажут потенциал.

Причина: прогноз множества величин сложнее и может потребовать отдельной
нормализации, функции ошибки и нового слоя торгового правила.

## Проверки

### Проверка сортировки

Нужно подтвердить:

- training/offline preprocessing сортирует `fractal*` так же, как runtime;
- `fractal0` в benchmark соответствует тому же левому фракталу, который будет
  доступен в live;
- направление из `fractal0.direction` совпадает после сортировки.

### Проверка признаков

Для каждого поля нужно явно отметить:

- используется как входной признак;
- используется только как target;
- исключено из-за будущей информации;
- исключено как бессмысленное для текущей цели.

### Проверка target-ов

Для каждой target family считаем:

- долю положительных target;
- пересечение с offline `label_all().signal`;
- распределение по годам;
- BUY/SELL баланс;
- средний будущий результат в ATR.

### Торговая проверка

Для каждого варианта:

1. threshold candidate выбирается только на validation;
2. старый score threshold не меняется;
3. test проверяется frozen;
4. sequential test проверяет ограничение на пересекающиеся сделки.

Метрики:

- trades;
- PF;
- win rate;
- mean pnl ATR;
- yearly PF;
- number of negative years;
- sequential trades;
- sequential PF.

## Критерии успеха

Вариант считается перспективным, если:

- frozen test PF > 1.2;
- sequential test PF > 1.1;
- нет сильной зависимости от одного года;
- число сделок достаточно для оценки, ориентир: не меньше 100 на test;
- направление не берётся из offline `signal`;
- candidate-source можно воспроизвести из текущей строки `Nero.csv`.

Вариант считается слабым, если:

- PF около 1 или ниже;
- положительный результат держится на одном году;
- почти все сделки отбрасываются и остаётся слишком малая выборка;
- candidate сильно повторяет `label_all().signal`, но не объясняется текущей
  строкой фракталов.

## Риски

1. **Скрытое заглядывание вперёд.**
   Нужно отдельно проверить каждую группу полей.

2. **Переобучение на validation.**
   Сетка параметров должна быть ограниченной. Test используется один раз после
   выбора.

3. **Слабое направление.**
   Направление из `fractal0.direction` может быть недостаточным. Но в этой
   спецификации оно фиксировано как часть стратегии.

4. **Сложность признаков.**
   Сырые `fractal0..fractal99` лучше не отдавать модели сразу без агрегатов:
   будет трудно понять, что найдено.

5. **Многозадачное обучение.**
   Target Family E может быть сильнее, но сложнее. Его нельзя смешивать с
   первым этапом без отдельного плана.
