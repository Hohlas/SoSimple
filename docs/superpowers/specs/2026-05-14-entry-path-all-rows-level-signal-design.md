# Entry Path All-Rows Level Signal Design

> **Date**: 2026-05-14
> **Status**: Draft
> **Track**: Entry path candidate-source audit
> **Goal**: Спроектировать live-safe правило `signal_candidate` по всей строке фракталов, проверить его отдельно, а затем проверить как связку со старым score-фильтром.
> **Related materials**: `docs/reports/2026-05-14-entry-path-all-rows-ranking.md`, `docs/reports/2026-05-14-entry-path-causal-surrogate.md`, `docs/reports/2026-05-14-entry-path-direct-bar-model.md`, `docs/DATA_FLOW.md`

## Контекст

Текущий `entry_path_v1_live_safe` не использует будущие признаки во входе
модели. Но экспорт торговых сигналов всё ещё зависит от:

```python
selected = (frame["signal"] != 0) & (score >= threshold)
```

В offline `signal` построен через `label_all()` и использует полный исторический
файл. В live raw `Nero.csv` этот `signal` равен нулю. Значит такой `signal`
нельзя считать готовым production-кандидатом сделки.

Первый all-rows benchmark уже показал отрицательный результат: просто убрать
`signal != 0`, взять направление из `fractal0.direction` и применить старый
`pred_ret_24_dir_atr` нельзя. На test PF был ниже 1.

Вывод: нужен не простой all-rows gate, а новый live-safe источник
`signal_candidate`, который отвечает на вопрос:

> находится ли цена `fractal0.price` на сильном уровне?

## Связь с прямой моделью

Эта спецификация проверяет отдельную гипотезу: можно ли найти сильный уровень
по текущей строке фракталов и использовать его как candidate-source.

Она не заменяет direct-bar подход, где модель сама выбирает:

```text
SELL / SKIP / BUY
```

Отчёт `2026-05-14-entry-path-direct-bar-model.md` сейчас является важной
базой сравнения. Он слабый, но архитектурно ближе к production, потому что не
фиксирует направление через `fractal0.direction`.

Любой winner из этой спецификации обязан сравниваться минимум с:

| Baseline | Test PF | Sequential PF | Trades / sequential trades |
|---|---:|---:|---:|
| all-rows ranking | 0.9134 | 0.5908 | 329 / 133 |
| causal surrogate | 1.1537 | 1.4111 | 36 / 31 |
| direct bar model | 1.1141 | 1.1334 | 1277 / 274 |

Если level-candidate даёт PF выше 1, но хуже direct-bar baseline по
устойчивости, числу сделок или sequential test, это не считается улучшением.

## Основная идея

Одна строка `Nero.csv` содержит текущую отсортированную строку фракталов:

```text
fractal0, fractal1, ..., fractal99
```

`fractal0` — новый левый фрактал после сортировки. Его собственные поля почти
не описывают силу уровня. Из `fractal0` для торгового решения напрямую берём
только:

- `fractal0.direction` — направление сделки;
- `fractal0.price` — координата уровня, относительно которой анализируется вся
  строка фракталов.

Сила уровня определяется окружением вокруг `fractal0.price`: какие рядом есть
фракталы, как они расположены по цене, какие у них направления, сила, пробои,
историческая реакция цены и возраст.

Новый `signal_candidate` должен строиться по всей строке фракталов. Если
candidate найден, направление сделки задаётся так:

```text
fractal0.direction == -1 -> BUY
fractal0.direction ==  1 -> SELL
```

Старый score текущей модели не должен скрывать качество нового candidate-source.
Поэтому каждый вариант проверяется в двух режимах.

Сначала отдельно, без старой модели:

```python
selected = signal_candidate != 0
```

Затем со старым score-фильтром:

```python
selected = (signal_candidate != 0) & (score >= original_threshold)
```

`original_threshold` берётся из прошлого frozen rule без нового подбора. Если
candidate-source слаб сам по себе, но выглядит хорошо только после score-фильтра,
это нужно явно записать как зависимость от старой модели.

## Термины

**Строка фракталов** — одна строка `Nero.csv` после сортировки `fractal*`.

**Уровень** — область цены вокруг `fractal0.price`, а не точная цена одним
числом.

**Сильный уровень** — уровень, после касания которого с повышенной вероятностью
возникает отскок в сторону сделки.

**Candidate-source** — правило или модель, которая решает, есть ли вообще
кандидат сделки. Это не финальный торговый сигнал.

**Score-фильтр** — старая модельная оценка, например `pred_ret_24_dir_atr`,
которая применяется только после появления candidate.

**Direct-bar baseline** — проверка, где модель сама выдаёт `SELL / SKIP / BUY`
для строки, без фиксированного направления из `fractal0.direction`.

## Временная корректность

Входные признаки должны быть доступны в текущей строке `Nero.csv`.

Согласно `docs/DATA_FLOW.md`, поля `Up/Dn` внутри `fractal*` формируются в
`lib_PIC.mqh` инкрементально:

- новый уровень создаётся в `NEW_LEVEL()`;
- `LEVELS_FIND_AROUND()` обновляет `Up/Dn` только по уже прошедшим барам;
- `NERO_CSV_CREATE()` записывает в строку только состояние, известное на момент
  этой строки.

Значит `Up/Dn` старых фракталов можно использовать как исторические признаки,
если они уже находятся в текущей строке. В первом feature set они включаются
для `fractal1..fractal99`, потому что это единственный прямой источник
исторической реакции цены на соседние уровни.

Но будущие `up_3..dn_48` для текущего `fractal0` можно использовать только как
цели обучения, а не как входные признаки.

Отдельный инвариант: `fractal0` является самым новым фракталом после сортировки.
Для него `Up/Dn` в текущей строке ожидаемо равны нулю или близки к нулю, потому
что реакция цены на этот новый уровень ещё не накопилась. Поэтому:

- `fractal0.Up/Dn` не используются как признаки силы текущего уровня;
- `fractal1..fractal99.Up/Dn` используются как признаки окружения уровня;
- будущие `up_3..dn_48` для `fractal0` используются только как цели обучения.

## Требования

1. Работать только с отсортированной строкой фракталов.
2. Проверить, что offline preprocessing и runtime preprocessing дают одинаковую
   сортировку `fractal0..fractal99`.
3. Направление сделки брать только из `fractal0.direction`.
4. `fractal0.price` использовать только как точку отсчёта для анализа других
   фракталов.
5. `label_all().signal` использовать только как сравнительную метку, но не как
   production-сигнал.
6. Каждый candidate-source сначала проверять отдельно, без старого score.
7. Затем проверять тот же candidate-source со старым score и старым threshold.
8. Старый score и старый threshold не подбирать заново в первой итерации.
9. Добавить новую разметку target families, не изменяя `label_all()`.
10. Добавить отдельную нормализацию нового набора признаков, не смешивая её
    бездумно со старой rowwise-нормализацией.
11. Перед обучением посчитать частоты target families на train/validation.
12. Перед использованием старого score-фильтра сравнить распределение score в
    новом candidate universe со старым `signal != 0` universe.
13. Любые параметры нормализации нового набора признаков fit только на train.
14. Test запускать один раз после frozen validation choice.
15. Любой winner сравнивать с all-rows, causal surrogate и direct-bar
    baseline.
16. Все торговые проверки выполнять теми же метриками, что в предыдущих тестах:
   PF, число сделок, win rate, средний PnL в ATR, годы, sequential test.

## Нецели

В этой спецификации не меняются:

- MT4 execution;
- формат `ml_signals.csv`;
- старый checkpoint `entry_path_v1_live_safe`;
- frozen threshold старого score-фильтра;
- `label_all()` как историческая разметка.

При этом будет добавлен новый слой разметки для target families A-E. Старый
`label_all()` остаётся только для сравнения и диагностики.

Также это не production approval. Цель этапа — исследовать candidate-source.

## Ранние проверки перед полной матрицей

Полная матрица target/input вариантов запускается только после ранних проверок.

### Проверка 1: live-safe признаки

До обучения нужно подтвердить:

- offline и runtime сортировка дают тот же `fractal0`;
- `fractal1..fractal99.Up/Dn` читаются из текущей сырой строки, а не из
  артефакта после разметки;
- для всех используемых фракталов выполняется:

```text
fractal_time <= row_time
```

- `fractal0.Up/Dn` исключены из входных признаков;
- будущие `up_3..dn_48` для `fractal0` используются только как цели обучения.

Если эта проверка не пройдена, обучение candidate-моделей не запускается.

### Проверка 2: направление

До матрицы A/C/D нужно проверить `fractal0.direction` против обратного
направления, BUY-only и SELL-only.

Если направление:

- не лучше обратного;
- имеет PF <= 1.0;
- имеет correct direction rate около 50%;
- даёт явный отрицательный вклад по BUY-only или SELL-only,

то полная матрица с фиксированным `fractal0.direction` не запускается. Следующий
шаг тогда не level-candidate с фиксированным направлением, а:

- модель `SELL / SKIP / BUY`;
- или отдельные BUY-only и SELL-only candidate-source.

### Проверка 3: частота целей

Для каждой target family до обучения считаются:

- positive rate на train;
- positive rate на validation;
- число positive samples на train;
- число positive samples на validation;
- распределение positive samples по годам.

Ориентиры:

```text
positive rate >= 3%
train positives >= 500
validation positives >= 100
major validation/test years >= 20 positives
```

Если target не проходит эти ориентиры, он не идёт в основной benchmark и
остаётся только диагностикой.

### Проверка 4: лимит первого прохода

Первый проход ограничен заранее:

```text
Входы:
- zones
- nearest K=16
- zones + nearest K=16

Цели:
- A: быстрый отскок
- C: отскок с ограниченным риском
- D: trailing-прибыль

Варианты признаков:
- geometry + old-fractal Up/Dn
- geometry-only контроль
```

Target B остаётся диагностическим вариантом и не входит в обязательный первый
проход. `K=8`, `K=32`, `Input C` и `Input D` переносятся во второй этап.

## Признаки уровня

### Нормализация относительно `fractal0.price`

Для каждого фрактала `fractali` считаем:

```text
raw_distance_atr = (fractali.price - fractal0.price) / ATR
abs_distance_atr = abs(raw_distance_atr)
```

Так модель не видит абсолютную цену инструмента. Она видит структуру уровня
относительно текущего `fractal0.price`.

Дополнительно проверяется направленная система координат:

```text
trade_dir = +1 для BUY
trade_dir = -1 для SELL
directed_distance_atr = trade_dir * raw_distance_atr
```

Смысл: BUY и SELL ситуации зеркалируются. Для BUY положительное расстояние
означает цену выше уровня; для SELL положительное расстояние означает цену ниже
уровня, то есть тоже движение в сторону сделки.

В первой итерации нужно сравнить три варианта:

- только `raw_distance_atr`;
- только `directed_distance_atr`;
- оба признака вместе.

### Входные представления

Нужно не смешивать разные способы подачи фракталов в модель. Проверяются
отдельные семейства входных признаков.

#### Input A: зоны вокруг уровня

На вход модели подаются не все 100 фракталов, а сводные признаки по ценовым
зонам вокруг `fractal0.price`.

Сами зоны:

Строятся агрегаты по ценовым зонам:

```text
0.00..0.25 ATR
0.25..0.50 ATR
0.50..1.00 ATR
1.00..2.00 ATR
2.00..4.00 ATR
```

Для каждой зоны считаются:

- количество фракталов;
- количество верхних и нижних фракталов;
- количество same-direction и opposite-direction фракталов относительно
  направления сделки;
- количество `strong`;
- количество пробитых и непробитых;
- сумма и максимум `power`;
- средний и максимум `count`;
- максимум `impulse`;
- сумма исторической реакции `Up/Dn` для `fractal1..fractal99`, если поле уже
  накоплено в текущей строке.

Фракталы дальше `4 ATR` в этом варианте не попадают в детальные зоны. Чтобы не
терять информацию о краях строки, добавляются грубые признаки:

- `outside_4atr_count`;
- `outside_4atr_strong_count`;
- `outside_4atr_power_sum`;
- количество фракталов выше `fractal0.price`;
- количество фракталов ниже `fractal0.price`.

#### Input B: ближайшие фракталы по цене

Берутся не `fractal8`, `fractal16` или `fractal32` по номеру колонки.
Алгоритм другой:

1. распарсить все `fractal0..fractal99`;
2. посчитать `abs(fractali.price - fractal0.price) / ATR`;
3. отсортировать фракталы по этому расстоянию;
4. взять ближайшие `K` по цене.

Базовое значение первого этапа:

```text
K = 16
```

`K = 8` и `K = 32` не входят в первый обязательный проход. Их можно добавить
во второй итерации, если `K=16` покажет потенциал.

Для каждого ближайшего фрактала сохраняются:

- `distance_atr`;
- `direction`;
- `same_direction`;
- `strong`;
- `break`;
- `reverse`;
- `power`;
- `count`;
- `impulse`;
- `fractal_atr`;
- накопленные `Up/Dn` этого фрактала, если это не `fractal0` и значения уже
  есть в текущей строке.

Если валидных фракталов меньше `K`, недостающие места заполняются нулями и
отдельным `mask`-признаком:

```text
nearest_07_valid = 0 или 1
```

#### Input C: все 100 фракталов с относительной ценой

В этом варианте на вход подаются все `fractal0..fractal99`, но цена каждого
фрактала заменяется на:

```text
raw_distance_atr
directed_distance_atr
```

Проблема: `fractal0.price` может быть на краю диапазона всех цен строки. Это не
ошибка, а важное состояние уровня. Поэтому добавляются признаки:

- rank позиции `fractal0.price` среди цен всех фракталов;
- количество фракталов выше `fractal0.price`;
- количество фракталов ниже `fractal0.price`;
- расстояние до ближайшего фрактала выше;
- расстояние до ближайшего фрактала ниже.

#### Input D: фракталы внутри `X * ATR`

Берутся только фракталы:

```text
abs(fractali.price - fractal0.price) <= X * ATR
```

Здесь возникает переменное число фракталов на строку. Для первой реализации не
нужно делать модель с переменной длиной входа. Нужно выбрать один из простых
вариантов:

- агрегировать такие фракталы по зонам, как в Input A;
- либо взять максимум `K` ближайших внутри окна, дополнить нулями и `mask`.

Рекомендуемый первый набор входов:

```text
Input A: только зоны
Input B: ближайшие K=16 по цене
Input A + Input B(K=16): смешанный вариант
```

`Input C` и `Input D` оставить как второй этап, если первый набор покажет
потенциал.

### Нормализация нового набора признаков

Новый набор признаков не должен использовать статистики validation/test.

Правило:

```text
fit normalization/statistics only on train
apply frozen train statistics to validation/test
```

Для локальных признаков вроде `raw_distance_atr` отдельный scaler может быть не
нужен. Но если используются percentile, cap, standardization или другие общие
параметры, они fit только на train.

Это обязательный leakage-invariant для нового feature set.

### Признаки реакции цены

Для старых фракталов `fractal1..fractal99` поля `Up/Dn` считаются исторической
реакцией цены на уровень. Их можно агрегировать по зонам:

- средний и максимальный favorable move;
- средний и максимальный adverse move;
- отношение favorable/adverse;
- число фракталов, где favorable заметно больше adverse.

Для BUY:

```text
favorable = Up
adverse = Dn
```

Для SELL:

```text
favorable = Dn
adverse = Up
```

Для `fractal0` эти признаки не строятся: его `Up/Dn` не описывают силу уровня в
момент появления.

## Цели обучения

Цели строятся для `fractal0`, но не попадают во вход модели.

Для всех целей используются:

```text
fav_H = движение в сторону сделки за H баров
adv_H = движение против сделки за H баров
```

Для BUY:

```text
fav_H = up_H
adv_H = dn_H
```

Для SELL:

```text
fav_H = dn_H
adv_H = up_H
```

### Target Family A: быстрый отскок

Цель:

```text
adv_6 < N * ATR
fav_6 >= Y * ATR
```

Смысл: за первые 6 часов цена дала сильный ход в сторону сделки и не прошла
против нас дальше стопа.

Проверяемая сетка:

```text
N = 1.5, 2, 3
Y = 2, 3, 4
```

### Target Family B: ступенчатый отскок

Цель:

```text
fav_6  >= 1 * X * ATR
fav_12 >= 2 * X * ATR
fav_24 >= 3 * X * ATR
fav_48 >= 4 * X * ATR
```

Смысл: уровень дал движение, которое развивалось по времени, а не было
одиночным шумовым выбросом.

В первом проходе эта цель считается диагностической. Она не входит в
обязательную матрицу, чтобы не раздувать перебор вариантов.

Проверяемая сетка:

```text
X = 0.5, 0.75, 1.0
```

### Target Family C: отскок с ограниченным риском

Цель:

```text
fav_24 >= X * ATR
adv_12 <= Y * ATR
```

Смысл: уровень дал достаточно большой ход в сторону сделки, но раннее движение
против сделки было ограничено.

Проверяемая сетка:

```text
X = 3, 4, 5
Y = 1.5, 2, 3
```

### Target Family D: trailing-прибыль

Цель:

```text
trailing stop N * ATR закрыл сделку по стопу с профитом >= Z * ATR
```

Смысл: цена достаточно ушла в сторону сделки, стоп подтянулся, затем откат
закрыл сделку в плюс. Это учитывает путь цены, а не только максимум движения.

Target D строится только по OHLC path, а не из `fav/adv`. Причина: `fav/adv`
показывают максимальные движения внутри горизонта, но не знают порядок движения
цены.

Правило расчёта:

```text
entry = open следующего бара после строки сигнала
далее последовательный проход по OHLC барам
BUY: best_high, stop = best_high - N * ATR
SELL: best_low, stop = best_low + N * ATR
```

Логика должна совпадать с `simulate_trailing_stop_exit()` и торговым benchmark.
Иначе цель будет выглядеть как execution-aware, но фактически будет построена
из неполной информации о пути цены.

Проверяемая сетка:

```text
N = 2, 3, 4, 5
Z = 1, 2, 3
horizon = 24, 48
```

Важно: старая цель вида `fav_24 - adv_24 >= X * ATR` не используется как
основная. Она может принять плохую сделку, где цена сначала ушла против нас на
много ATR, а потом восстановилась.

### Target Family E: прогноз величин

Модель предсказывает не один класс, а набор величин:

```text
fav_3, fav_6, fav_12, fav_24, fav_48
adv_3, adv_6, adv_12, adv_24, adv_48
trail_pnl_* для выбранных N/horizon
```

Потом торговое правило строится поверх прогнозов. Например:

```text
pred_fav_24 >= 4 ATR
pred_adv_12 <= 2 ATR
```

Этот путь сложнее, но может лучше использовать связь между горизонтами.

## Подходы к моделированию

### Подход 1: простые правила

Строим признаки уровня и подбираем пороги вручную или через grid search.

Плюсы:

- проще объяснить;
- проще найти ошибку;
- меньше риск переобучения.

Минусы:

- может не увидеть сложные сочетания признаков.

### Подход 2: классификатор сильного уровня

Модель получает признаки уровня и предсказывает вероятность target family:

```text
P(strong_level)
```

Candidate появляется, если:

```text
P(strong_level) >= candidate_threshold
```

Плюсы:

- лучше подходит для сложной структуры уровня;
- можно сравнить разные цели A-D одной и той же процедурой.

Минусы:

- нужно аккуратно выбирать порог на validation;
- нужна проверка важности признаков.

### Подход 3: прогноз величин

Модель предсказывает `fav/adv/trail_pnl`, а затем правило выбирает сделки.

Плюсы:

- наиболее гибкий путь;
- модель не привязана к одному бинарному target.

Минусы:

- сложнее обучение;
- сложнее интерпретация;
- нужен отдельный слой торгового правила.

## Рекомендуемый первый этап

Первым этапом делать не полный neural retrain, а ограниченную исследовательскую
матрицу. Порядок фиксированный:

1. Пройти проверку live-safe признаков.
2. Пройти проверку направления.
3. Пройти проверку частоты целей.
4. Если ранние проверки пройдены, запустить ограниченную матрицу:
   - `Input A`: только зоны;
   - `Input B`: ближайшие `K=16` по цене;
   - `Input A + Input B(K=16)`: смешанный вариант;
   - target families A/C/D;
   - основной вариант `geometry + old-fractal Up/Dn`;
   - контрольный вариант `geometry-only`.
5. Candidate direction брать только из `fractal0.direction`.
6. Сначала проверить candidate-source отдельно, без старого score:

```python
signal_candidate != 0
```

7. Затем сравнить распределение старого score:

```text
old universe: signal != 0
new universe: signal_candidate != 0
all rows
```

8. Если распределение score в новом universe сильно отличается от старого,
    старый threshold считается только диагностикой, а не production-кандидатом.
9. После этой диагностики проверить тот же candidate-source со старым score:

```python
score >= original_threshold
```

10. Выбрать winner только на validation.
11. Запустить test один раз после frozen validation choice.
12. Сравнить winner с all-rows, causal surrogate и direct-bar baseline.

Target Family E оставить вторым этапом, если A-D покажут потенциал.

Причина: прогноз множества величин сложнее и может потребовать отдельной
нормализации, функции ошибки и нового слоя торгового правила.

## Проверки

### Проверка сортировки

Нужно подтвердить:

- training/offline preprocessing сортирует `fractal*` так же, как runtime;
- `fractal0` в benchmark соответствует тому же левому фракталу, который будет
  доступен в live;
- направление из `fractal0.direction` совпадает после сортировки.

### Проверка признаков

Для каждого поля нужно явно отметить:

- используется как входной признак;
- используется только как target;
- исключено из-за будущей информации;
- исключено как бессмысленное для текущей цели.

Отдельный audit для `Up/Dn`:

- `fractal1..fractal99.Up/Dn` должны читаться из текущей raw-строки;
- нельзя брать их из post-labeling артефакта;
- для каждого используемого фрактала проверяется `fractal_time <= row_time`;
- `fractal0.Up/Dn` исключаются из признаков;
- future `up_3..dn_48` для `fractal0` допускаются только как target.

### Проверка направления

Перед обучением нужно проверить, насколько `fractal0.direction` вообще полезен
как направление сделки.

Проверки:

1. Для каждой строки сравнить результат сделки по `fractal0.direction` и по
   обратному направлению.
2. Посчитать, как часто направление `fractal0.direction` даёт лучший `fav/adv`,
   чем обратное направление.
3. Посчитать простую торговую проверку без модели:

```text
вход на каждом валидном fractal0.direction
```

4. Отдельно посчитать BUY-only и SELL-only результаты.

Если направление из `fractal0.direction` окажется слабым, следующий вариант
модели должен предсказывать не `0/1`, а:

```text
-1 = SELL
 0 = SKIP
 1 = BUY
```

Для первой итерации `fractal0.direction` остаётся фиксированным источником
направления, но его качество должно быть измерено.

Критерии отказа от `fractal0.direction` как единственного источника направления:

- baseline по `fractal0.direction` имеет PF <= 1.0;
- направление не лучше обратного направления;
- correct direction rate близок к 50%;
- BUY-only или SELL-only даёт явно отрицательный вклад и портит общий результат.

В этом случае следующий этап должен проверять альтернативы:

- направление по балансу верхних/нижних фракталов в зоне `0..1 ATR`;
- направление по same/opposite-direction плотности вокруг `fractal0.price`;
- модель с выходом `SELL/SKIP/BUY`.

### Проверка target-ов

Для каждой target family считаем:

- долю положительных target;
- если positive rate < 3%, цель не идёт в основной benchmark;
- число positive samples на train;
- число positive samples на validation;
- число positive samples по годам;
- пересечение с offline `label_all().signal`;
- распределение по годам;
- BUY/SELL баланс;
- средний будущий результат в ATR.

Частоты считаются до обучения моделей. Это предотвращает ситуацию, где модель
обучается на слишком редком target и даёт внешне красивый, но статистически
слабый результат.

Минимальные ориентиры:

```text
train positives >= 500
validation positives >= 100
major validation/test years >= 20 positives
```

### Проверка размерности признаков

Для каждого входного представления нужно посчитать:

- число признаков;
- число строк в validation candidate universe;
- отношение `features / validation_candidates`.

Ориентир первого этапа:

```text
features / validation_candidates < 1:10
```

Если отношение хуже, вариант считается рискованным по переобучению и должен
быть упрощён: меньше зон, меньше полей, один `K`, либо больше регуляризации.

### Проверка score-фильтра

Перед применением старого threshold нужно сравнить score distribution:

- на старом universe `signal != 0`;
- на новом universe `signal_candidate != 0`;
- на всех строках.

Сравниваются минимум:

- count;
- mean;
- median;
- std;
- p10/p25/p75/p90;
- доля строк выше `original_threshold`.

Если median score нового universe сместилась относительно старого больше чем
примерно на `2 * std(old universe)`, это красный флаг. В таком случае старый
threshold нельзя считать переносимым production-правилом; его можно использовать
только как диагностический фильтр.

Даже если `candidate + old score` даёт хороший PF, это не production approval.
Роль старого score-фильтра в этой спецификации — проверить совместимость с
прошлой моделью, а не доказать торговую пригодность нового candidate-source.

### Торговая проверка

Для каждого варианта:

1. threshold candidate выбирается только на validation;
2. сначала проверяется candidate отдельно, без старого score;
3. затем проверяется распределение старого score в новом candidate universe;
4. затем проверяется candidate + старый score-фильтр;
5. старый score threshold не меняется;
6. test проверяется frozen;
7. sequential test проверяет ограничение на пересекающиеся сделки.

Метрики:

- trades;
- PF;
- win rate;
- mean pnl ATR;
- yearly PF;
- number of negative years;
- sequential trades;
- sequential PF.

### Сравнение с базовыми результатами

Каждый validation winner после frozen test сравнивается с результатами
2026-05-14:

| Baseline | Test PF | Sequential PF | Trades / sequential trades |
|---|---:|---:|---:|
| all-rows ranking | 0.9134 | 0.5908 | 329 / 133 |
| causal surrogate | 1.1537 | 1.4111 | 36 / 31 |
| direct bar model | 1.1141 | 1.1334 | 1277 / 274 |

Цель не только получить PF > 1, но и понять, даёт ли level-candidate реальное
улучшение относительно уже проверенных путей.

## Критерии успеха

### Исследовательский проход

Вариант считается исследовательски перспективным, если:

- frozen test PF > 1.2;
- sequential test PF > 1.1;
- нет сильной зависимости от одного года;
- число сделок достаточно для оценки, ориентир: не меньше 100 на test;
- направление не берётся из offline `signal`;
- candidate-source можно воспроизвести из текущей строки `Nero.csv`.
- результат не хуже direct-bar baseline по смысловым метрикам или объясняет
  иной полезный режим с достаточным числом сделок.

### Production-кандидат

Вариант считается production-кандидатом только после дополнительных проверок:

- учтены spread, commission, slippage;
- есть MT4 parity;
- проверен drawdown;
- нет сильной зависимости от одного года;
- есть confidence interval или bootstrap по сделкам;
- подтверждено исполнение на том же типе выхода, под который обучался target.

Вариант считается слабым, если:

- PF около 1 или ниже;
- положительный результат держится на одном году;
- почти все сделки отбрасываются и остаётся слишком малая выборка;
- candidate сильно повторяет `label_all().signal`, но не объясняется текущей
  строкой фракталов.

## Риски

1. **Скрытое заглядывание вперёд.**
   Нужно отдельно проверить каждую группу полей.

2. **Переобучение на validation.**
   Сетка параметров должна быть ограниченной. Test используется один раз после
   выбора. Первый этап ограничивается `K=16` для ближайших фракталов; `K=8/32`
   не добавляются, пока базовая версия не покажет потенциал. Target B также не
   входит в обязательный первый проход.

3. **Слабое направление.**
   Направление из `fractal0.direction` может быть недостаточным. Поэтому перед
   обучением нужна отдельная проверка против обратного направления.

4. **Сложность признаков.**
   Сырые `fractal0..fractal99` лучше не делать единственным первым входом:
   будет трудно понять, что найдено. Первый этап должен включать объяснимые
   зоны, ближайшие `K=16` по цене и их связку. Если отношение
   `features / validation_candidates` хуже `1:10`, представление нужно
   упрощать.

5. **Многозадачное обучение.**
   Target Family E может быть сильнее, но сложнее. Его нельзя смешивать с
   первым этапом без отдельного плана.

6. **Непереносимость старого score threshold.**
   Старый score обучался на другом candidate universe. Если score distribution
   на новом universe сильно отличается от старого `signal != 0` universe,
   старый threshold используется только как диагностика.

7. **Смешение с direct-bar направлением.**
   Level-candidate с фиксированным `fractal0.direction` не должен подменять
   direct-bar подход. Если direct-bar baseline остаётся лучше, level-candidate
   считается исследовательской веткой, а не заменой production-контура.
