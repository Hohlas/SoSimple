## T3. Снять фильтр signal != 0

### Контекст (почему это проблема)

В `ML/limit_order_train.py:44-50` обучающая выборка фильтруется:

```python
buy = df[signal == 1].copy()                     # только BUY-сигналы
fill_mask = buy['buy_fill_lag'] != -1             # только заполненные лимитники
result = buy[fill_mask].copy()                    # ~5 000 строк
```

**Почему это ограничение избыточно:**

1. Исторически signal — это strong-фрактал, который MT4 считает "значимым разворотом". Модель училась только на "интересных" моментах.

2. В limit-order конвенции signal НЕ используется для входа. Вход — это pending лимитный ордер на Close[row]. Решение о входе принимает модель (через порог на предсказание), а не колонка signal.

3. Строки с signal=0 (нет strong-фрактала) — валидные точки входа. Лимитник можно поставить на любой строке.

4. Transformer с 305 000 параметров на 5 000 строках дал AUC=0.5 (случайный результат). 5 000 строк — категорически мало для Transformer. Без фильтра будет ~55 000 строк — достаточно для начального обучения.

**Важное уточнение:** `benchmark_limit_order_entry.py` (RF baseline) НЕ фильтрует по signal — он использует все строки с `fill_lag != -1`. Проблема только в `limit_order_train.py` (Transformer).

### Действия

**Файл:** `ML/limit_order_train.py`

1. В функции `prefilter_csv()` (строки 44-50) убрать фильтр `signal == 1`:
   ```python
   # Было:
   buy = df[signal == 1].copy()
   fill_mask = buy['buy_fill_lag'] != -1
   result = buy[fill_mask].copy()

   # Стало:
   fill_mask = df['buy_fill_lag'] != -1
   result = df[fill_mask].copy()
   ```

2. Добавить в лог количество строк после фильтрации для сравнения с предыдущими запусками.

**Проверка:** запустить скрипт на одном файле, убедиться что количество строк выросло с ~5k до ~55k. Колонка target (`buy_sl3_tp3`) должна содержать все три значения (0, 1, -999 для NO_FILL).

**Методика уже содержит Ablation Study Protocol** (`docs/methodology/08-model-development.md:59-88`), но он ни разу не применялся к engineered признакам.

2. Обучить RF (`n_estimators=100, max_depth=10, random_state=42` — те же параметры, что baseline) на вариантах:

## T5. Добавить правила отбора признаков в методику

### Контекст (почему это проблема)

Текущая методика (`docs/methodology/`) описывает процесс проверки признаков на утечку будущего (leakage gate), но **не содержит правил отбора признаков по информативности**. Это приводит к практике "запихиваем всё подряд":

- 233 engineered признака без проверки корреляций
- Признаки-производные (Pwr = min(Frnt, Back); Strong = f(Pwr)) дублируют информацию
- Нет процедуры исключения шумовых признаков

**Что должно быть в методике:**

1. Перед обучением — корреляционный фильтр (удаление одного из пары с |r| > 0.95)
2. После обучения — фильтр важности (feature importance из RF, удаление < 0.5% вклада)
3. Абляция групп (protocol уже есть в `08-model-development.md:59-88`, но он не обязателен — нужно сделать обязательным)
4. Правило избыточности: если признак B полностью вычисляется через признак A, A и B не должны использоваться вместе (пример: Pwr и Frnt/Back)

### Действия

**Файл:** `docs/methodology/03-feature-contract-leakage.md` (добавить секцию "Feature Selection Gate") или создать `docs/methodology/03b-feature-selection.md`

Добавить:
1. **Корреляционный фильтр:** перед обучением — матрица корреляций. Пары с |r| > 0.95 — удалить один признак (менее информативный или производный).
2. **Фильтр важности:** после RF — удалить признаки с важностью < 0.5% от суммарной. Переобучить без них. Сравнить validation PF.
3. **Обязательная абляция:** для любой группы признаков (>5 шт.) — обучить модель без группы, сравнить с baseline. Без улучшения → группа не принимается.
4. **Правило производных признаков:** если признак B = f(признак A), использовать только A. Примеры: Pwr = min(Frnt, Back) → оставить Frnt и Back. Strong = f(Pwr) → оставить Frnt и Back.
5. **Принцип минимальности:** новый признак принимается только если его удаление ухудшает validation-метрику.

## T6. Добавить Shift в lib_PIC.mqh и Python-парсинг

### Контекст (почему это нужно)

Текущий порядок фракталов в строке — нумерация 0..99. Но fractal5 и fractal6 могут быть разделены 1 баром или 50 барами. Нумерация не отражает реальную временную плотность.

Функция `SHIFT(timestamp)` в MQL4 возвращает количество баров от текущего до указанного времени. `SHIFT(F[f].T)` — сколько баров назад сформировался фрактал f.

**Что даёт Shift:**
- Для fractal0: shift = 0 (текущий бар, всегда)
- Для fractal1: shift = несколько баров (когда был предыдущий разворот)
- `delta_shift[i] = shift[i] - shift[i+1]` — временной зазор между соседними фракталами в барах

**Почему это полезнее нумерации:**
- Отражает плотность разворотов: частые развороты → маленький delta_shift → высокая волатильность
- Для Transformer: естественное позиционное кодирование (вместо/вместе с time_pos)
- Для RF: дополнительный признак, несущий информацию о рыночном режиме

**Нормализация Shift:**
- Абсолютный shift (0..10000+): `log(1 + shift)` — логарифм сжимает хвост
- delta_shift (1..500+): piecewise linear-log с порогами p50, p85, p99 (как для front/back в `normalize.py`)

**Обратная совместимость:** существующие CSV имеют 22 поля. Старые файлы должны читаться без ошибок — для отсутствующего 23-го поля shift = 0.
