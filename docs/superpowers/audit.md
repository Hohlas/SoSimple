## Замечания

### 1. Важно — полная сумма profit по TX_CLOSE (−1755.1) существует в данных, но нигде не раскрыта

- Место: отчёт, разделы «Результаты» и «forbidden_interpretations»;
  metrics JSON (`profit_sum`).
- Суть: отчёт ограждает `profit_sum=242.5`, но это сумма по 18 старым
  polling-CLOSE (7% закрытий). Теперь в артефакте есть полное покрытие:
  сумма `profit` по 269 TX_CLOSE = −1755.1 (пересчитано по CSV). Ни отчёт,
  ни манифест, ни metrics JSON это число не публикуют и не ограждают.
- Доказательство: `df[df.event=='TX_CLOSE'].profit.sum() == -1755.1`;
  `df[df.event=='CLOSE'].profit.sum() == 242.5`; в metrics JSON только
  `profit_sum: 242.5`.
- Почему важно: методика 16 — отчёт с PnL-подобными числами обязан их
  ограждать; сейчас опубликовано менее репрезентативное число (242.5),
  а более полное (−1755.1) молча доступно любому, кто откроет CSV.
  Следующий читатель либо сделает из него неогороженный вывод, либо
  заподозрит замалчивание. Замечу: DEAL_PROFIT не включает swap/commission —
  и это тоже нигде не оговорено.
- Рекомендация: одной строкой в Results и в манифест: «сумма profit по 269
  TX_CLOSE = −1755.1 (без swap/commission), DIAGNOSTIC_ONLY, не PnL-вывод»;
  добавить в forbidden_interpretations. Либо обновить `profit_sum` в парсере
  на TX-покрытие с явной пометкой семантики.

### 2. Важно — INI-конфиг полного прогона не сохранён в repo

- Почему важно: методика 16 — «Все источники результата доступны»,

### 3. Улучшение — legacy-поля metrics JSON противоречат reconciliation без пометки

- Место: `mt5_execution_metrics_20260731_tx_lifecycle.json`:
  `missing_open_estimate: 42`, `open_without_close_estimate: 234` рядом с

- Суть: старые оценки считаются только по polling-потоку (294−252, 252−18)

- Доказательство: содержимое metrics JSON (строки `missing_open_estimate`,

- Почему важно: методика 16 — расхождение отчёт↔artifact блокирующее;

- Рекомендация: переименовать/пометить поля (`polling_*`) или добавить в

  и заменены reconciliation».

### 6. Вопрос — последний отложник пережил max_fill_lag_bars=6 более чем на сутки

- Место: отчёт, «Арифметика размещений» («1 остаток на конце теста»).
- Суть: сирота-размещение поставлено 2022.11.30 22:00 и по строкам
  `position_or_pending_order_exists` всё ещё существовало 2022.12.02 08:00 —
  ~34 часа спустя, при `max_fill_lag_bars=6`. Либо у отложников нет
  брокерской экспирации (тогда 9 ORDER_EXPIRED возникли по другому
  механизму), либо expiry-логика не сработала для последнего ордера.
  Классификация «остаток на конце теста» построчно верна (моя трассировка
  подтвердила: это единственное размещение без исхода), но причина
  выживания не классифицирована.
- Доказательство: трассировка размещение→исход по CSV (293/294 имеют исход);
  `MT5_LogLifecycleForCurrentState` логирует ORDER_EXPIRED только когда
  pending уже исчез И срок истёк (`lib_ML_Signal.mqh`, ветка
  `buy_pending==0 && sell_pending==0 && ... > MT5_LastPlacedExpiry`) —
  живой просроченный pending события не порождает.
- Почему важно: мелкая, но незакрытая дыра в семантике «expiry»: события
  ORDER_EXPIRED не означают «ордер снят по сроку», а «исчез и срок истёк».
  При batch-этапе с большим числом правил это исказит статистику отказов.
- Рекомендация: зафиксировать в Limitations одной строкой; при следующем
  изменении executor — ставить экспирацию на сам ордер
  (ORDER_TIME_SPECIFIED) или снимать просроченный pending явно.

### 7. Вопрос — таблица сравнения не включает OPEN_FAILED / ORDER_EXPIRED / INIT

- Место: отчёт, таблица «Результаты».

  разбивку 8682+32), ORDER_EXPIRED 9/9, INIT 1/1 — вывод верен, но

- Доказательство: пересчёт по обоим event CSV.
- Почему важно: методика 16 — ключевые числа сверяются со structured
  artifact; полные счётчики есть в манифесте, так что это не блокер,
  но таблица создаёт впечатление полного сравнения.
- Рекомендация: добавить три строки в таблицу или сноску «остальные события
  идентичны, полные счётчики в манифесте».
