> **Аудитируемый документ**: `docs/audit/brainstorm-workflow.js` (рабочая версия, не закоммичена: `git diff` = +327/−208 строк)
> **Суть изменений**: замена схемы «2 независимых критика на идею + детерминированное слияние вердиктов» на схему «спор автор×критик на кластер (до 3 раундов) + синтез-арбитр с правом только понижать вердикты».

## 2. Сильные стороны версии (по коду)

- **Связка результат↔вектор по индексу** (строки 138–150): `parallel` возвращает массив с `null` на месте упавших агентов, `filter(Boolean)` до `map` не применяется — индексация не съезжает. Правильно.
- **Источник истины — `rawIdeas`** (строки 221–228): кластерный агент возвращает только имена и номера кластеров, формулировки не переписываются — заявленная защита от «поглощения при слиянии» реально обеспечена кодом.
- **Потерянные при разметке идеи логируются** (строки 222–225), а не исчезают молча.
- **Все JSON-ответы проходят `parseJson`** с очисткой markdown-обёрток и fallback-извлечением `{...}` из текста (строки 34–48); падение одного спора не рвёт весь workflow (строки 344–350, 382–389, 447–456).
- **Вердикты валидируются против белого списка** `ALLOWED_VERDICTS` (строки 450–452, 479–481); мусорный вердикт → статус «без спора», а не тихий проход.
- **Полный артефакт пишется ДО применения потолка `MAX_CLUSTERS`** (строки 243–262 → 266–270): `brainstorm-ideas.md` содержит все идеи.

## 3. Замечания

### 3.1 [КРИТИЧНО] Падение фазы 2 при отсутствии поля `tags` у гипотезы

- **Место**: строка 252 (`ideasMd`: ``Теги: ${h.tags.join('; ')}``).
- **Суть**: генераторам `tags` заказан как массив (строка 124), но приёмный фильтр (строка 145) требует только `h.name && h.essence`. Если хотя бы один генератор вернёт гипотезу без `tags` (или с `tags: null`), строка 252 бросает `TypeError: Cannot read properties of undefined (reading 'join')` — весь workflow падает в фазе 2, уже после затратной фазы генерации.
- **Доказательство**: в том же файле то же поле в двух других местах защищено — строка 175: `Array.isArray(h.tags) ? h.tags.join('; ') : ''` и строка 296 аналогично. Строка 252 — единственная незащищённая точка; значит, автор знает о нестабильности поля, но здесь защита пропущена. Это не гипотеза: для падения достаточно одного отсутствующего поля в ответе LLM — регулярно возникающий случай.
- **Почему важно**: однопроходный workflow без рестарта; падение теряет все результаты фазы 1.
- **Исправление**: на строке 252 ``Теги: ${Array.isArray(h.tags) ? h.tags.join('; ') : ''}``; опционально — нормализовать при приёме (строка 145): `h.tags = Array.isArray(h.tags) ? h.tags : []`.

### 3.2 [ВАЖНО] Кластеры, отброшенные потолком `MAX_CLUSTERS`, исчезают из итогового документа молча

- **Место**: строки 266–270 (усечение `clusters.length = MAX_CLUSTERS`).
- **Суть**: отброшенные кластеры не попадают ни в `debates` (строка 300 идёт уже по усечённому массиву), ни в `protocolBlock` для арбитра (строка 513). Арбитр физически не может их упомянуть: инструкция «идеи со статусом "без спора" выведи отдельным примечанием» (строки 565–566) покрывает только то, что есть в протоколах. Итог: в `brainstorm-filtered.md` этих идей нет вообще, след остаётся только в runtime-логе и в полном `brainstorm-ideas.md` без пометки об отбросе.
- **Доказательство**: трассировка данных — единственный источник для арбитра есть `protocolBlock` (строка 544), построенный из `merged` ⊂ `debates` ⊂ усечённого `clusters`. Имена отброшенных пишутся только в `log(...)` (строка 269), который в файл не попадает.
- **Почему важно**: противоречит принципу «ничего не терять молча» и усложняет воспроизводимость: читатель итогового документа не узнает, что кластеры сверх потолка не оценивались.
- **Исправление**: передавать арбитру список отброшенных кластеров отдельным блоком («не оценивались из-за потолка стоимости») для вывода примечанием; либо дописывать этот список в `brainstorm-ideas.md`.


### 3.4 [ВАЖНО] Статус «спор не состоялся» может отобразиться как «нефальсифицируема»

- **Место**: строки 490–492 (`falsifiable: d.final && d.final.falsification ? ... : false`) в связке со строкой 510.
- **Суть**: для кластеров со статусом `no_debate` (упал агент раунда 1 или 3) `falsifiable=false`, фальсификация `null`. Арбитр получил инструкцию «[нефальсифицируема] — в конец списка с объяснением» (строка 564). Если агент-арбитр интерпретирует отсутствие фальсификации у «без спора»-записи по этому правилу, технический сбой будет представлен как свойство идеи («нефальсифицируема»), а не как ошибка исполнения.
- **Доказательство**: в `protocolBlock` для `no_debate` выводится только «СПОР НЕ СОСТОЯЛСЯ (ошибка агента). Вердикт: без спора.» (строка 519); отдельного запрета применять к ним правило «[нефальсифицируема]» в промпте арбитра нет.
- **Почему важно**: подмена причины (сбой агента → «идея нефальсифицируема») — ровно тот класс искажений, против которого построен анти-сговорный контур.
- **Исправление**: в инструкции арбитру явно указать: «записи "без спора" — технический сбой; не помечать их как нефальсифицируемые».

### 3.5 [ВАЖНО] Ошибка критика при «убита за переупаковку» неисправима

- **Место**: строки 551–553 («ПОВЫШАТЬ вердикты запрещено: если критик убил идею, она остаётся убитой») + строка 575 («не воскрешай убитые идеи»).
- **Суть**: единственный сценарий, где вердикт «убита» выносится по проверяемому факту (цитата из ретроспективы, строки 325–329), одновременно единственный, где возможна объективная ошибка: критик привёл неточную цитату или аналог с другим механизмом edge. Арбитр уполномочен проверить цитату (строки 546–548), но при подтверждении ошибки не имеет права исправить вердикт — идея остаётся убитой.
- **Доказательство**: в промпте критика совпадение темы прямо объявлено недостаточным («нужна точная цитата... описывающая тот же механизм», строки 326–328) — значит, риск ложного срабатывания признан; но механизма коррекции ложного срабатывания нет. Это проектное решение, помечаю как вопрос к нему, а не как баг.
- **Почему важно**: цель брэйншторма — поиск новых источников edge; асимметричное правило систематически занижает выход и не имеет предохранителя именно в самом проверяемом случае.
- **Исправление (на усмотрение)**: разрешить арбитру одно исключение — повышение «убита» → «условно», только если цитата критика проверена по ретроспективе и заведомо не описывает тот же механизм edge, с обязательной записью в раздел 4 документа.

### 3.6 [УЛУЧШЕНИЕ] Верификация итогового файла слишком слабая

- **Место**: строки 592–599.
- **Суть**: проверка — только «файл существует и ≥ 150 слов». Документ, где арбитр написал одно предложение и таблицу без списков убитых/понижений, пройдёт проверку. Заказанная структура из 4 разделов (строки 556–572) не контролируется.
- **Доказательство**: код проверки — `ls -l` и `wc -w`, больше никаких assert'ов (строки 594–596).
- **Исправление**: добавить в промпт верификации `grep -c '^## '` и/или проверку наличия ключевых разделов («Таблица-сводка», «Список убитых»).

### 3.7 [УЛУЧШЕНИЕ] Результат записи `brainstorm-ideas.md` не проверяется

- **Место**: строки 255–262.
- **Суть**: агенту поручена запись промежуточного артефакта, его ответ не читается и не проверяется. При отказе/сбое записи единственный полный артефакт фазы 2 отсутствует, а workflow продолжается; фаза 5 проверяет только `brainstorm-filtered.md`.
- **Доказательство**: результат вызова не присваивается ни одной переменной (строка 255: `await agent(...)` без приёма).
- **Исправление**: добавить `brainstorm-ideas.md` в проверку фазы 5 (`ls` + `wc -w`).

### 3.8 [УЛУЧШЕНИЕ] Неразличимые сценарии «защита не распарсилась» и «автор промолчал»

- **Место**: строки 382–389.
- **Суть**: при сбое парсинга/пропуске раунда 2 подставляется `defense = { concession: false, accepted_arguments: [], defense: normalizeResult(defenseRaw) }`; при `defenseRaw == null` это пустая строка. Раунд 3 получает пустой «ответ автора», и критик по правилу «если защита не добавила ничего содержательного — сохрани предварительный вердикт» (строки 424–426) сохраняет вердикт. Поведение разумное, но неотличимо в протоколе от содержательного, но слабого ответа; в `protocolBlock` выведется «Раунд 2 (защита автора): —».
- **Доказательство**: строка 528 рендерит `d.defense.defense || '—'` — маркер технического сбоя теряется.
- **Исправление**: при fallback помечать в протоколе «(технический сбой парсинга / ответа не было)».

### 3.9 [УЛУЧШЕНИЕ] Протокол арбитра не показывает предварительный вердикт раунда 1

- **Место**: строки 513–537 (`protocolBlock`).
- **Суть**: анти-сговорное правило «вердикт меняется ТОЛЬКО под новые аргументы» (строки 424–426) аудиторски не проверяемо по протоколу: в `head` выводится только финальный вердикт критика (строка 517), `preliminary_verdict` из атаки (строка 340) в протокол не входит. Арбитр не видит, изменил ли критик вердикт в раунде 3 и под какие аргументы.
- **Доказательство**: поле `preliminary_verdict` заказывается в раунде 1 (строка 340), но в `protocolBlock` используются только `attack.novelty`, `attack.vulnerabilities`, `attack.falsification` (строки 523–525).
- **Исправление**: добавить в строку атаки протокола `Предварительный вердикт: ${d.attack.preliminary_verdict}` — это даст арбитру основание для понижения при необоснованном смягчении.

### 3.10 [УЛУЧШЕНИЕ] Вторая попытка `JSON.parse` без собственного catch

- **Место**: строки 41–46 (`parseJson`).
- **Суть**: если первый `JSON.parse` не удался и извлечён фрагмент между первой `{` и последней `}`, второй `JSON.parse` (строка 44) находится вне блока `try` и бросает собственное низкоуровневое исключение вместо читаемого `label + ': не удалось извлечь JSON'`.
- **Доказательство**: строка 44 вне `try` (блок заканчивается `catch` на строках 40–41) — исключение propagates с другим сообщением.
- **Почему важно**: косметика — ошибки всё равно логируются с именем спора (строки 346–349 и др.), но диагностика ухудшается.
- **Исправление**: обернуть второй `JSON.parse` в тот же try/catch и бросать стандартизированное сообщение.


### 3.12 [ВОПРОС] Интерполяция сгенерированного агентом текста в последующие промпты без ограничения длины

- **Место**: строки 361–364, 417–421, 544.
- **Суть**: JSON-ответы раундов и весь `protocolBlock` вставляются в промпты следующих агентов как есть, без ограничения длины. Для данного controlled-контура (все участники — субагенты одного запуска) это допустимо, но при 20 кластерах с полным `JSON.stringify(attack)` + `JSON.stringify(defense)` размер `protocolBlock` не ограничен сверху и теоретически способен приблизиться к пределу контекста арбитра (~150K).
- **Доказательство**: лимитов на длину полей в промптах раунда 3 нет (в раунде 2 есть «до 200 слов», строка 375 — только на ответ автора); оценка размера протокола — расчётная гипотеза, не замер.
- **Исправление**: при необходимости — ограничить длину полей при сборке `protocolBlock` (обрезка по N символов на поле).
