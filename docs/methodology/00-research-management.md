## 0. Управление исследованием

### Цель

Убрать произвол из процесса: до запуска экспериментов должно быть понятно, что проверяется, по каким данным, какими метриками и на каком основании кандидат будет принят или отклонён.

### Входы

- продуктовая цель и ограничения проекта;
- актуальный pipeline данных;
- предыдущие отчёты и открытые риски;
- список доступных источников данных;
- предполагаемый торговый контур.

### Пошаговые действия

1. Назвать исследовательскую гипотезу одной фразой.
2. Зафиксировать тип задачи: direction, regression, take/skip, barrier outcome, execution policy, signal filter.
3. Зафиксировать единицу решения: строка датасета, бар, фрактал, уровень, сигнал или сделка.
4. Зафиксировать `decision_time`: open/close бара, таймфрейм, инструмент, момент входа.
5. Зафиксировать execution convention до обучения:
   - тип входа: market, limit, stop или другой;
   - цена входа: close/current, next open, limit price, Bid/Ask;
   - fill/no-fill rule и допустимый fill lag;
   - canonical spread и stress grid без zero-spread как trading gate;
   - правила для commission, slippage, latency, missed opens;
   - единица PnL: пункты, ATR/R-multiples или деньги.
6. Заранее задать gate-критерии: PF, число сделок, минимальное число сделок в год, просадка, отрицательные годы, BUY/SELL устойчивость, baseline uplift.
7. Заранее определить, что будет считаться провалом.
8. Создать короткую запись о гипотезе, split-протоколе, метриках и expected artifacts.

### Уровни исследования

Любой эксперимент принадлежит к одному из двух уровней. Уровень фиксируется до запуска и указывается в отчёте (см. [16-reporting-audit.md](16-reporting-audit.md)).

| Уровень | Цель | Пороги | Максимальный verdict |
|---|---|---|---|
| Поисковый (exploratory) | Генерация гипотез: широкий перебор идей, профилей, целей, горизонтов, правил и инструментов | Пороги можно ослаблять; search budget фиксируется и раскрывается; результат не доказывает качество | `DIAGNOSTIC_ONLY` или `research_only` |
| Проверочный (confirmatory) | Проверка одной заранее зафиксированной гипотезы | Предзарегистрированные числовые пороги; заморожены цель, признаки, преобразования, модель, правило, пороги, инструменты и split | `candidate` или `reject` |

Переход из поискового уровня в проверочный требует нового плана с замороженными условиями. Нельзя задним числом поднять статус поискового результата до кандидата: это скрытое переопределение verdict.

Поисковый уровень разрешает широкий поисковый перебор, если до запуска очередной партии задана граница поиска: какие семейства признаков, цели, горизонты, модели, инструменты и параметры перебираются. Граница может быть широкой, но не должна расти после просмотра промежуточных результатов без новой записи в плане. Каждая запись добавляется в `cumulative_search_budget` исследовательской ветки, а не обнуляет риск подгонки.

Поисковый уровень не отменяет дисциплину split: `locked_test` не используется для выбора, leakage-проверки обязательны, а любой holdout без замороженных правил используется только как disclosure. Он ослабляет только интерпретацию результата: найденный лучший вариант становится гипотезой для проверки, а не кандидатом.

Проверочный уровень запускается только после поискового вывода или заранее сформулированной идеи. В нём правила фиксируются до запуска, затем проверяются без подбора на новых данных: другом периоде, другом источнике данных и/или заранее выбранных валютных парах. Проверка на другой паре полезна как проверка переносимости, но сама по себе не снимает риск подгонки исходного поиска.

### Обязательные проверки

- Гипотеза не менялась после просмотра `locked_test`.
- Уровень исследования (поисковый/проверочный) зафиксирован до запуска и указан в отчёте.
- Проверочный уровень использует предзарегистрированные числовые пороги, а не fuzzy-критерии без чисел.
- Для поискового уровня указан текущий и накопленный search budget; максимальный verdict не выше `research_only`.
- Для проверочного уровня указаны замороженные правила и набор данных/инструментов, на которых они проверяются без подбора.
- До запуска заданы минимальные `sample_size_gate`: строки/события для обучения и сделки/сигналы после всех фильтров для validation/locked_test/forward.
- `locked_test` не используется как validation.
- Для каждого будущего результата заранее известен allowed verdict.
- Любой результат с неясным feature contract помечается `DIAGNOSTIC_ONLY`.
- Любой результат с неясным или нереалистичным execution convention помечается `DIAGNOSTIC_ONLY`.
- Zero-spread запуск допустим только как `DIAGNOSTIC_ONLY` для отладки механики и не может закрывать trading gates.
- Если изменение `entry_price`, spread, fill policy или PnL convention меняет labels, candidate selection или frozen rule, это новый ML-цикл, а не пересчёт метрик.

### Критерии успешного завершения

- Есть проверяемая гипотеза.
- Есть список метрик и gate-порогов.
- Есть план, какие данные относятся к train, validation, `locked_test` и forward.
- Известно, какие артефакты должны быть сохранены.

### Типовые ошибки

- Начинать с выбора модели вместо постановки торгового решения.
- Подбирать цель или порог после просмотра `locked_test`.
- Считать высокий PF доказательством без аудита признаков.
- Смешивать механическую диагностику MT4 с доказательством качества ML.
- Проводить проверочный прогон с fuzzy-порогами без чисел: каждый критерий без заранее зафиксированного числового значения открывает дорогу подгонке решения под желаемый исход.
- Превращать поисковый результат в кандидата без нового проверочного цикла.

### Ветвления

- Если `decision_time` неизвестен: остановить ML-часть и описать торговый контур.
- Если execution convention неизвестен: остановить ML-часть или проводить только diagnostic run без verdict.
- Если критерии успеха не заданы: проводить только поисковый анализ без verdict.
- Если задача меняется после `locked_test`: открыть новый экспериментальный цикл с новым закрытым проверочным периодом.
