## 6b. Oracle-preflight: проверка потолка торговой постановки

### Цель

До обучения моделей проверить, есть ли у выбранной торговой постановки теоретический потенциал.

Oracle-preflight (проверка потолка) намеренно использует будущие labels вместо предсказаний модели. Это утечка будущего, поэтому результат имеет только диагностический смысл. Он отвечает на вопрос: если бы модель знала нужные будущие события идеально, дала бы сама механика сделки положительный результат после издержек?

Этот этап нужен до `baseline-first`, чтобы не тратить время на обучение модели для механики, которая не даёт прибыль даже при идеальном знании будущего.

### Место в pipeline

Выполнять как можно раньше, но только после того, как уже зафиксированы:

- `decision_time`;
- target contract;
- execution contract: entry, stop, take-profit, timeout, spread, fill policy;
- train/validation split;
- симулятор сделки или другой измеритель PnL.

Нельзя выполнять oracle до разметки целей и торгового правила: иначе неизвестно, какие будущие факты подставлять и как считать PnL.

### Входы

- train split;
- validation split, если он уже выделен;
- target labels, построенные по будущим данным;
- trading protocol;
- cost model;
- заранее заданная сетка постановок: сторона, горизонт, offset, stop-rule, take-profit-rule и другие параметры, если они есть.

### Пошаговые действия

1. Зафиксировать, какие будущие labels будут использоваться как oracle-значения.
   - Примеры: истинный факт пробоя стопа, истинный будущий favorable move, истинный close reason.
   - Эти поля должны быть явно помечены как `future-derived` и запрещены для feature contract.
2. Запустить **oracle всех условий**.
   - Для каждой заранее заданной постановки подставить все ключевые будущие условия одновременно.
   - Аналог для Fractal Stop: одновременно использовать истинный `stop_broken_flag` и истинный `target_val`.
   - Цель: проверить полный теоретический потолок механики.
3. Если oracle всех условий не проходит gates на канонических издержках — остановить цикл.
   - В этом случае проблема в торговой постановке, а не в модели.
   - Дальше нужно менять механику сделки, а не архитектуру модели.
4. Если oracle всех условий проходит gates — выполнить **oracle-выбор постановки**.
   - Перебрать заранее заданную сетку: BUY/SELL, H, offset и другие параметры постановки.
   - Выбрать лучшие зоны только внутри разрешённого research split.
   - Минимальный безопасный вариант: выбор по train, подтверждение на validation.
5. Зафиксировать выбранную постановку как проектное решение.
   - Например: `SELL`, `H=12`, `offset=0.5`.
   - После этого обычная модель должна обучаться только на live-safe признаках.
6. Сохранить oracle report:
   - какие labels использовались как oracle;
   - какие параметры перебирались;
   - какие costs применялись;
   - PF/PnL/trades по train и validation;
   - разрезы по годам и сторонам;
   - вывод: `mechanics_pass`, `mechanics_fail` или `inconclusive`.

### Обязательные проверки

- Test split не используется для oracle-выбора.
- Oracle-значения не попадают в признаки, cache, вход модели, export или MT4.
- Сетка side/H/off задаётся до запуска oracle-выбора постановки.
- Канонические издержки являются главным gate; zero-spread может быть только diagnostic.
- Результат oracle не считается качеством модели и не повышает verdict кандидата.
- Если validation используется для выбора side/H/off, этот validation уже участвовал в выборе постановки. Для последующей независимой проверки модели нужен отдельный split или явно сниженный статус результата.
- Oracle всех условий проверяет все ключевые условия вместе, а не по отдельности.
- Oracle-выбор постановки не скрывает провал по годам, стороне или малому числу сделок.
- Если PF получается бесконечным из-за нулевых убытков, обязательно проверить число сделок и первые сделки вручную.

### Критерии успешного завершения

Статус `PASS` означает только: торговая постановка имеет подтверждённый диагностический потолок и её имеет смысл передавать в baseline/model этап.

Минимальные условия:

- oracle всех условий проходит PF/PnL gates на канонических издержках;
- стресс-издержки не уничтожают результат полностью или причина чувствительности описана;
- trades/year не ниже заранее заданного минимума;
- результат не держится на одном годе, одной стороне или единичных сделках;
- выбранная side/H/off-зона подтверждена не только на train.

Статус `FAIL`:

- oracle всех условий не проходит канонические издержки;
- результат существует только при zero-spread;
- результат держится на малом N или одном режиме;
- невозможно отделить oracle labels от live-safe features.

Статус `DIAGNOSTIC_ONLY`:

- oracle запущен только для понимания механики;
- split был уже частично использован для выбора;
- нет достаточной устойчивости для проектного решения.

### Типовые ошибки

- Считать oracle PF доказательством торговой стратегии.
- Выбирать side/H/off по test.
- После oracle-выбора считать тот же validation полностью независимым.
- Использовать oracle labels как признаки или нормализовать их вместе с признаками.
- Сравнивать модель с oracle как с реальным baseline.
- Делать вывод по zero-spread, если production execution имеет spread.
- Перебирать бесконечную сетку до нахождения красивого PF.

### Ветвления

- Если oracle всех условий `FAIL`: закрыть механику или сформулировать новую постановку.
- Если oracle всех условий `PASS`, но model baseline слабый: проблема в признаках или модели.
- Если oracle всех условий сильный только для одной стороны/H/off: зафиксировать узкую постановку и проверять её как отдельную гипотезу.
- Если oracle `PASS`, но обычная модель не даёт PF: выполнить feature audit, ablation или перейти к другой модели.
