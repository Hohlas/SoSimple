## 6. Временное разделение и протокол валидации

### Цель

Защититься от утечки будущего через split и обеспечить честную проверку во времени.

### Входы

- подготовленный датасет;
- timestamps;
- target horizon;
- planned validation/locked_test/forward windows.

### Канонические периоды SoSimple

Исторический split по умолчанию состоит из трёх крупных частей:

| Период | Роль |
|---|---|
| `train` | обучение модели, fit scaler, feature audit |
| `validation` | поиск, подбор и выбор гипотезы |
| `locked_test` | один запуск замороженного правила без подбора |

`diagnostic_holdout`, `test`, `frozen test` и `OOS` не должны быть отдельными обязательными историческими кусками. Если правила не заморожены, такой период является только disclosure. Если правила заморожены, это `locked_test`.

`forward` не отрезается из истории: это только данные после даты принятия решения.

Физические файлы могут сохранять старые имена. Например, `DATA/Nero_test_labeled.csv` является кандидатом на роль `locked_test` только если он не использовался для выбора признаков, целей, модели, порогов, входа/выхода или нормализации. Если использовался — это disclosure/invalidated holdout, а не `locked_test`.

### Пошаговые действия

1. Отсортировать строки по времени в направлении, соответствующем pipeline.
2. Задать `train`/`validation`/`locked_test` границы датами и индексами.
3. Проверить, что shuffle временных строк не применяется.
4. Если label horizon пересекает границу split: применить embargo gap ИЛИ письменно доказать, что ни один label/результат не пересекает границу.
5. Если проводится hyperparameter search, использовать только train/validation.
6. Если нужен walk-forward, заранее задать rolling или expanding windows.
7. Сохранить split manifest и `sample_size_gate`.

### Внутреннее разделение validation

Если validation используется одновременно для model selection, подбора торгового правила и финальной оценки, эти роли должны быть явно указаны:

- **val-stop**: для действий, влияющих на модель — early stopping, выбор числа деревьев/эпох, ablation winner.
- **val-select**: для подбора торговых параметров, threshold/top-k/grid и выбора rule-family.
- **val-eval**: для финальной оценки уже выбранного правила перед `locked_test`.

Это роли, а не обязательно отдельные календарные периоды. Если данных мало, роли можно объединить в один большой `validation`, но результат не выше `RESEARCH_ONLY`, пока правило не проверено на `locked_test` или заранее заданном walk-forward.

### Sample size gate

До запуска задать минимумы по каждому периоду и проверить их после всех фильтров:

- `train`: число raw rows, независимых событий/объектов, классов/сторон;
- `validation`: число строк/сигналов/сделок для каждой роли `val-stop`, `val-select`, `val-eval`, если роли разделены;
- `locked_test`: число сделок/сигналов всего, по годам и по BUY/SELL;
- `forward`: минимальный N для verdict; если N меньше, статус только `watch`.

Дефолтные нижние границы, если в плане не заданы более строгие:

- `train_raw_rows >= 1000`, `train_independent_events >= 300` и минимум `100` наблюдений каждого класса/стороны для supervised-задачи;
- `validation_trades_after_filters >= 100` и минимум `30` сделок на активную сторону;
- `locked_test_trades_after_filters >= 100` и минимум `30` сделок на активную сторону;
- сделки покрывают минимум `3` календарных месяца; иначе результат считается regime-local diagnostic;
- для годовых выводов: минимум `30` сделок в год, иначе годовой срез только diagnostic.

Для sequence-моделей и фрактальных профилей не привязывать gate к числу input columns или токенов: строки соседних событий не считаются независимыми автоматически. Если gate не пройден: обучение/подбор можно запускать только как `DIAGNOSTIC_ONLY`; winner не может стать `candidate`.

#### Особенности событийного ряда (event-driven данных)

Для данных, где строка формируется при наступлении события (новый фрактал, сделка, сигнал), а не через фиксированный интервал:
- Интервал между строками непостоянен. Одна строка может покрывать часы, другая — дни. Статистики «сделок в год» должны интерпретироваться с учётом неравномерности.
- Эволюционирующие признаки одного физического объекта могут присутствовать в нескольких строках с разными значениями. Убедиться, что split не создаёт ситуацию, где будущее состояние объекта попадает в train.
- Если validation и `locked_test` находятся в систематически разных рыночных условиях (например validation — ranging, `locked_test` — тренд), validation-based winner selection ненадёжен. В этом случае требуется walk-forward с несколькими окнами или expanding window для снижения режимной зависимости; одной проверки distribution-характеристик недостаточно.

### Обязательные проверки

- Validation используется для выбора модели, признаков, порогов и правил.
- `locked_test` открывается только для `frozen_rule_for_locked_test`.
- Forward включает только данные после даты принятия решения.
- Нельзя объединять `locked_test` и forward задним числом.
- `sample_size_gate` посчитан на финальном universe объектов после фильтров, а не на raw rows.

### Критерии успешного завершения

- Есть явные даты и размеры `train`/`validation`/`locked_test`.
- Каждый период проходит `sample_size_gate` или статус результата понижен.
- Есть правило, что можно подбирать на validation.
- Есть правило, что запрещено менять после `locked_test`.
- Есть план walk-forward или причина, почему он не нужен на данном этапе.

### Типовые ошибки

- Случайный split временного ряда.
- Многократный `locked_test` после каждого изменения.
- Называть старый `locked_test` forward validation.
- Подбирать threshold на `locked_test`, а потом заявлять OOS.

### Ветвления

- Если `locked_test` уже использован для выбора: нужен новый закрытый исторический период или strictly-forward период.
- Если validation/locked_test режимы сильно различаются: добавить walk-forward и regime analysis.
- Если forward данных нет: verdict `watch/no_forward_data`, не `confirmed`.
- Не разделять validation на `val-stop`, `val-select` и `val-eval` при одновременном early stopping, grid search и финальной оценке — приводит к завышенной validation-оценке.
