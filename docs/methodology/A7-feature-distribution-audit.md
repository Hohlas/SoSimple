# A7. Feature Distribution Audit

## Цель

Проверить, как каждый профиль признаков выглядит до обучения модели: диапазоны, хвосты, пропуски, сдвиг между периодами и технические артефакты mask/padding.

Эта проверка нужна до запуска обучения. Она отвечает на вопрос: модель получит осмысленное представление рынка или будет учить календарь, абсолютный ценовой режим, волатильность, padding либо ошибку feature builder-а.

## Когда обязателен

Feature Distribution Audit обязателен, если выполняется хотя бы одно условие:

- создаётся новый feature profile;
- меняется нормализация, scaler, clipping, `log1p` или signed-log;
- используется нейросеть, Transformer или sequence-вход;
- сравниваются `time`, `ATR`, `price`, `relative_price`, corridor/nearest/zones профили;
- отчёт показывает, что календарные признаки дают качество, близкое к полной модели;
- данные покрывают длинный исторический период, где абсолютная цена инструмента существенно изменилась.

## Контрольные профили

Контрольный профиль — это не торговый кандидат, а диагностический вход, который изолирует один источник сигнала.

| Профиль | Вход | Что проверяет |
|---|---|---|
| `time_only_clean` | только `hour_sin`, `hour_cos`, `dow_sin`, `dow_cos` | Сколько качества даёт календарь без цены, ATR и фракталов |
| `atr_only` | только `ATR` или заранее выбранный volatility-признак | Не является ли модель простым фильтром волатильности |
| `time_plus_atr` | `time_only_clean` + `ATR` | Отличить чистый календарь от календаря с режимом волатильности |
| `no_time` | основной профиль без календарных признаков | Сколько сигнала остаётся без календаря |
| `no_price` | основной профиль без абсолютной цены | Не вредит ли абсолютный ценовой режим |
| `relative_price_no_time` | цена как расстояние от anchor в ATR, без календаря | Чистая геометрия уровней |
| `relative_price_time` | то же + календарь | Добавляет ли календарь пользу поверх геометрии |

Если профиль называется `time_only`, в отчёте должно быть явно указано, входит ли туда `ATR`. Если входит, правильнее называть его `time_plus_atr`.

## Общий порядок

1. Зафиксировать список профилей до просмотра validation/holdout результата.
2. Построить финальные входы ровно тем же feature builder-ом, который будет использовать обучение.
3. Посчитать статистики на train и validation.
4. По train/validation принять решение: оставить профиль, исправить feature builder, применить другой scaler, clipping, `log1p` или signed-log.
5. Теми же правилами обработки применить профиль к test/holdout и посчитать сдвиг распределений.
6. Не менять профиль, scaler или clipping по результатам test/holdout. Test/holdout используется только для диагностики сдвига.
7. Если есть `ERROR`, обучение запрещено до исправления.
8. Если есть `WARNING`, обучение можно запускать только после явного решения: fix, rerun, accept-as-warning или reject profile.

## Статистики по каждому признаку

Для каждого признака и каждого split считать:

| Группа | Метрики |
|---|---|
| Покрытие | `n_valid`, `missing%`, `zero%` |
| Диапазон | `min`, `p1`, `p5`, `p25`, `p50`, `p75`, `p95`, `p99`, `max` |
| Масштаб | `mean`, `std` |
| Хвосты | `frac_abs_gt3`, `frac_abs_gt5`, `frac_abs_gt10`, `frac_abs_gt20` |
| Уникальность | `unique_count` или approximate unique count |
| Стабильность | constant/near-constant flag |
| Сдвиг | train->validation shift, train->holdout shift |

Для оценки асимметрии без сложной статистики достаточно сравнить:

```text
p95 - p50
p50 - p5
```

Если верхний хвост намного длиннее нижнего, рассмотреть `log1p` для неотрицательной величины или signed-log для signed-величины.

## Sequence и token-профили

Для sequence-входов считать статистики отдельно:

- по каждому token-field: `price_coord`, `direction`, `front`, `back`, и т.д.;
- по каждой позиции токена, если порядок имеет смысл: `token0`, `token1`, ...;
- по mask: сколько реальных токенов на строку;
- `padding%`;
- доля строк без валидных токенов;
- доля строк, где число токенов меньше ожидаемого;
- доля строк, где токены были обрезаны из-за `seq_len`.

Padding не является данными. Он не участвует в fit scaler и после normalization должен оставаться `0.0`.

## Corridor/nearest/zones профили

Для профилей вокруг anchor-уровня дополнительно считать:

| Метрика | Зачем |
|---|---|
| число фракталов в отборе: p5/p25/p50/p75/p95 | Проверка заполненности |
| доля строк с 0, 1, 2, 3+ фракталами | Защита от пустого контекста |
| доля строк с truncation | Не теряется ли большая часть структуры |
| `min_price_coord_atr`, `max_price_coord_atr` | Проверка границ коридора |
| распределение фракталов выше/ниже anchor | Проверка перекоса |

Для `corridor_10atr` ожидается:

```text
price_coord_atr = (price_i - price_0) / ATR
price_coord_atr примерно в диапазоне [-10, +10]
```

Если после отбора `corridor_10atr` есть значения далеко за пределами `[-10, +10]`, это ошибка отбора, ATR или парсинга.

Если координату дополнительно делят на ширину коридора:

```text
price_coord_unit = price_coord_atr / 10
```

то ожидаемый диапазон примерно `[-1, +1]`.

## Нормализация координаты цены

Абсолютная цена инструмента на длинном периоде может кодировать эпоху, а не структуру рынка. Для задач, где важна геометрия уровней вокруг `fractal0`, предпочтительная координата:

```text
price_coord_atr = (price_i - fractal0_price) / ATR
```

Для corridor-профилей это основной вариант. Абсолютную цену можно оставлять только как диагностический контроль.

Альтернативный диагностический вариант:

```text
price_coord_range = 2 * (price_i - min_price_in_profile) / (max_price_in_profile - min_price_in_profile) - 1
```

Если используется range-нормализация, обязательно добавить или отдельно отчитаться:

```text
corridor_width_atr = (max_price_in_profile - min_price_in_profile) / ATR
```

Иначе модель потеряет информацию о том, сжат ли рынок в 3 ATR или растянут на 15 ATR.

## ERROR

`ERROR` блокирует обучение.

| Флаг | Действие |
|---|---|
| `NaN` / `Inf` | Найти источник: парсинг, деление на ноль, ATR, логарифм, missing value |
| `PADDING_NOT_ZERO` | Исправить mask/padding; перенормализация не считается исправлением |
| Признак отсутствует в одном split | Исправить feature contract или исключить профиль |
| train scaler fit использует validation/test/holdout | Исправить pipeline; старый результат `DIAGNOSTIC_ONLY` |
| `corridor_Xatr` выходит за заявленные границы | Исправить отбор, ATR или формулу координаты |
| Значимая доля строк без валидных токенов | Профиль reject или изменить заранее заданный отбор |

## WARNING

`WARNING` не всегда означает ошибку, но требует явного решения до обучения.

| Флаг | Возможное решение |
|---|---|
| `TAIL_GT10` больше 1% | Рассмотреть `RobustScaler`, clipping или log/signed-log |
| любое `abs(x) > 20` | Проверить выбросы и источник значений |
| holdout p95 ушёл от train p95 больше чем на 3 train std | Зафиксировать regime shift; не подгонять scaler по holdout |
| `zero% > 95%` | Проверить, не мёртвый ли признак |
| near-constant | Исключить или оставить с обоснованием |
| corridor median < 3 фракталов | Профиль слишком бедный; расширить коридор в новом плане |
| слишком много truncation | Увеличить `seq_len` в новом плане или изменить правило отбора |

## Преобразования

Преобразования выбираются по train/validation audit, а не по test/holdout метрикам.

| Преобразование | Когда применять |
|---|---|
| `StandardScaler` | Базовый вариант для нейросетей, если нет длинных хвостов |
| `RobustScaler` | Много выбросов, медиана и квартильный диапазон стабильнее среднего/std |
| clipping `[-8, 8]` или `[-10, 10]` | Защитить нейросеть от редких экстремальных значений |
| `log1p(x)` | Неотрицательные величины с длинным правым хвостом: `shift`, ATR, расстояния без знака, счётчики |
| `sign(x) * log1p(abs(x))` | Signed-величины: signed distance, signed return, signed price coordinate |

Нельзя логарифмировать signed-величину обычным `log(x)`. Если величина бывает отрицательной, использовать signed-log или другой заранее заданный способ.

## Отчёт

Отчёт Feature Distribution Audit должен содержать:

- список профилей;
- список split;
- таблицу статистик по признакам;
- таблицу mask/padding/corridor coverage;
- список `ERROR` и `WARNING`;
- решение по каждому флагу;
- какие преобразования применены;
- на каком split принято решение;
- подтверждение, что test/holdout не использовался для выбора обработки;
- ссылку на structured artifact: JSON/CSV/parquet.

## Интерпретация

- Если `time_only_clean` близок к полной модели, полная модель может быть календарным фильтром.
- Если `atr_only` силён, модель может учить volatility regime.
- Если `time_plus_atr` сильно лучше `time_only_clean`, часть календарного эффекта на самом деле может быть волатильностью.
- Если `relative_price_no_time` слабый, а `relative_price_time` сильный, фрактальная геометрия не является главным источником сигнала в текущем профиле.
- Если `no_price` лучше профиля с абсолютной ценой, абсолютная цена вероятно добавляет режимный шум.
- Если corridor-профиль провален из-за малой заполненности, это не доказательство, что corridor-идея не работает; нужно сначала исправить покрытие.

## Типовые ошибки

- Считать нормализацию корректной только потому, что scaler применён.
- Проверять исходный CSV, но не финальный tensor/матрицу, которая реально идёт в модель.
- Называть профиль `time_only`, хотя в него входит `ATR`.
- Сравнивать time-профиль с фрактальным профилем, где price подан абсолютным уровнем на длинном историческом периоде.
- Делать вывод “фракталы слабее времени” без `relative_price`, `no_price` и corridor-контролей.
- Подбирать clipping или логарифмирование после просмотра holdout/test метрик.
- Считать padding реальными нулями.
- Менять ширину corridor после просмотра holdout результата.
