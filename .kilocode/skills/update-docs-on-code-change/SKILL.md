# Управление документацией

Создание, документирование и синхронизация docs при изменениях кода.

**Применяется к**: `*.py`, `*.mq4`, `*.mqh`, `*.ipynb`, `*.md`

**Маппинги код → docs**: [references/file-mappings.md](references/file-mappings.md)
**Шаблоны headers**: [templates/file-headers.md](templates/file-headers.md)

---

## Принципы

- Одна мысль = одно предложение
- Не дублируй между файлами — используй ссылки
- Используй таблицы вместо списков для сравнений
- Максимум 250 строк на документ (кроме справочников)
- Если документ > 300 строк: вынеси детали в отдельный файл, оставь резюме + ссылку

---

## Режим 1: Создание нового модуля

**Команда**: `create module [имя]`, `new script [имя]`

### Шаги

**Шаг 1: Определить параметры**
- Директория (processing / statistics / ML)
- Назначение (одна строка)
- Входные/выходные данные

**Шаг 2: Создать file header**

Использовать точный шаблон из [templates/file-headers.md](templates/file-headers.md):
- Python → `# ====` рамка (UTF-8)
- MQL4 → `//+--+` рамка (**UTF-16LE!**)
- Jupyter → Markdown ячейка (UTF-8)

**Шаг 3: Создать markdown документацию**

Создать `docs/[category]/[filename].md` по шаблону из [templates/file-headers.md](templates/file-headers.md) (секция "Markdown Documentation Template").

**Шаг 4: Обновить MODULE_INDEX.md**

Добавить строку в соответствующий раздел таблицы:
```markdown
| [file.py](path/file.py) | Назначение | `вход` → `выход` | [docs](docs/category/file.md) | ✅ |
```

Также обновить:
- `docs/DATA_FLOW.md` — если файл участвует в pipeline
- `AGENTS.md` — если критичный компонент

**Шаг 5: Валидация**
- Все поля header заполнены?
- Кодировка верная (MQL4: UTF-16LE)?
- Ссылки в документации работают?

---

## Режим 2: Документирование существующего модуля

**Команда**: `doc this [файл]`, `document [файл]`

### Шаги

1. Проверить наличие file header → если нет, создать по шаблону
2. Создать `docs/[категория]/[модуль].md` по шаблону (Режим 1, Шаг 3)
3. Добавить строку в таблицу MODULE_INDEX.md
4. Обновить DATA_FLOW.md если участвует в pipeline
5. Показать diff и запросить подтверждение

---

## Режим 3: Синхронизация документации

**Команда**: `sync docs`, `обнови документацию`, `синхронизируй docs`

### Шаги

**Шаг 1: Найти изменённые файлы**

Если пользователь явно указал файлы — использовать их. Иначе:
```bash
git diff --cached --name-only | grep -E '\.(py|mq4|mqh|ipynb|md)$'
```

**Шаг 2: Определить соответствующую документацию**

Использовать [references/file-mappings.md](references/file-mappings.md) для поиска соответствующего `.md` файла. Если `.md` не существует — предложить создать (Режим 1/2).

**Шаг 3: Обновить элементы документации**

В коде:
- Обновить поле `Обновлён:` в file header на текущую дату (YYYY-MM-DD)
- Обновить docstrings, если изменились сигнатуры функций

В связанном `.md` файле:
- Назначение — если изменилась функциональность
- Входные/выходные данные — если изменились форматы
- Использование — если изменились параметры запуска
- Примечания — новые ограничения или особенности

**Принцип Single Source of Truth**: детальная документация API → в docstrings кода; в `.md` — общее описание + ссылка на модуль.

В `docs/DATA_FLOW.md`:
- Обновить секцию Pipeline, если изменились входы/выходы шагов

В `CHANGELOG.md` (только при значимых изменениях):
- Добавлять ТОЛЬКО при: новых фичах, breaking changes, багфиксах, результатах экспериментов с выводами
- НЕ добавлять при: правках документации, рефакторинге без изменения поведения

**Шаг 4: Проверить размеры файлов**
```bash
wc -l <файл>
```
Если > 300 строк → предложить разбить на логические части.

**Шаг 5: Показать diff и запросить подтверждение**

Показать сводку изменений. Явно спросить: "Применить изменения? (yes/no)". Только после подтверждения вносить изменения.

## Режим 4: Валидация документации

**Команда**: `check docs`, `validate docs`

### Шаги

1. Найти все `.py`/`.mqh`/`.ipynb` файлы с file headers
2. Для каждого проверить:
   - Наличие соответствующего `.md` в docs/
   - Дата `Обновлён:` в header vs дата последнего изменения в git
   - Наличие в MODULE_INDEX.md
   - Размер `.md` файла (< 300 строк)
3. Вывести отчёт:

```
📊 ОТЧЁТ ПО ДОКУМЕНТАЦИИ:

📚 Документация к коду:
   ❌ processing/new_script.py — нет docs/processing/new_script.py.md
   ⚠️  processing/normalize.py — docs устарел (код изменён позже)
   ✅ processing/label_main.py — актуально

📏 Размеры .md файлов:
   ⚠️  docs/ML/neural_networks.md — 623 строки (рекомендуется разбить)

📋 MODULE_INDEX.md:
   ❌ processing/new_script.py — не найдена запись

📋 CHANGELOG.md:
   ⚠️  3 записи об изменениях документации (не по назначению)
```

---

## Quality Checklist

Перед завершением:

- [ ] File headers обновлены (поле `Обновлён:`)?
- [ ] Docstrings актуальны (совпадают с сигнатурами)?
- [ ] Markdown docs обновлены без дублирования docstrings?
- [ ] Каждый skill < 500 строк?
- [ ] CHANGELOG.md обновлён только для значимых изменений?
- [ ] MODULE_INDEX.md актуален?
- [ ] DATA_FLOW.md актуален (если изменился pipeline)?

---

## Common Mistakes

| Ошибка | Исправление |
|--------|-------------|
| Дублирование docstrings в .md | Добавь ссылку на файл, не копируй |
| CHANGELOG для каждого коммита | Только значимые изменения продукта |
| Файлы > 300 строк | Разбить на несколько файлов |
| Неверная кодировка MQL4 | Всегда UTF-16LE для `.mqh`/`.mq4` |
| Не проверять размеры после обновления | Всегда `wc -l` после правок |
