# Wiki Operations

Workflow для работы с LLM Wiki — слоем синтезированных знаний проекта.

## Когда использовать

- **Ingest**: после появления новых отчётов в `docs/reports/` — синтезировать выводы в wiki-страницы.
- **Save**: при обнаружении нового концепта или инсайта, который не укладывается ни в один существующий файл проекта.
- **Query**: в начале сессии или при исследовании темы — прочитать релевантные wiki-страницы для контекста.
- **Lint**: периодически или перед крупным этапом — проверить актуальность wiki-страниц.
- **Generate**: после любых изменений в файлах репо — обновить `wiki/REPO_integrity.md`.

## Принципы

1. **Wiki — persistent artifact**. Страницы живут между сессиями и накапливают знания. Это не scratch pad.
2. **LLM writes, Human directs**. Агент создаёт и обновляет страницы, пользователь решает что исследовать и когда.
3. **Знание компилируется один раз**. Если вывод получен из 5 отчётов, он записывается в wiki-страницу, а не пересинтезируется каждый раз.
4. **Wiki ≠ копия**. Страницы содержат только синтез, которому нет канонического места в проекте. Не дублировать:
   - Архитектуру → `AGENTS.md`, `docs/DATA_FLOW.md`
   - Модули → `MODULE_INDEX.md`
   - Текущее состояние → `CONTEXT_HANDOFF.md`
   - Сырые результаты → `docs/reports/`
5. **knowledge-rag ≠ source of truth**. MCP server `knowledge-rag` нужен для поиска кандидатов; выводы фиксируй только после чтения найденных первоисточников.

## Структура wiki/

```
wiki/
├── index.md          # Каталог wiki-страниц (LLM-maintained)
├── REPO_integrity.md # Integrity map всего репо (auto-generated)
├── log.md            # Append-only хронология операций
├── wiki.py           # Инструмент: generate / verify
├── research/         # Синтез отчётов из docs/reports/
└── concepts/         # Синтезированные концепты проекта
```

## Операции

### Ingest

Синтез новых отчётов в wiki-страницы.

**Hard rule:** если агент прочитал новые отчёты из `docs/reports/`, и они ещё не покрыты в `wiki/index.md`, операцию **Ingest** нужно довести до конца в этой же задаче. Если какой-то шаг не выполнен, агент должен прямо указать это и назвать причину.

1. Определи, какие отчёты из `docs/reports/` ещё не покрыты wiki-страницами (сравни с `wiki/index.md`).
2. Прочитай новые отчёты и существующие wiki-страницы по теме.
3. Реши: обновить существующую страницу или создать новую.
   - **Обновить**, если отчёт продолжает ту же линию исследования.
   - **Создать новую**, если отчёт открывает новое направление.
4. Напиши/обнови страницу (формат — см. ниже).
5. Если обнаружен новый концепт — создай страницу в `concepts/`.
6. Обнови `wiki/index.md` (добавь новые страницы, обнови покрытие).
7. Добавь запись в `wiki/log.md`.
8. Запусти `python wiki/wiki.py generate`.

### Save

Сохранение нового концепта или инсайта.

1. Убедись, что концепт действительно нуждается в wiki-странице (не дублирует существующий файл).
2. Создай страницу в `wiki/concepts/` (формат — см. ниже).
3. Обнови `wiki/index.md`.
4. Добавь запись в `wiki/log.md`.

### Query

Использование wiki как контекста.

1. Сначала прочитай `wiki/index.md`, чтобы понять существующий синтез.
2. Уточни поиск через MCP server `knowledge-rag`, tool `search_knowledge`.
3. Открой релевантные `wiki/research/`, `wiki/concepts/` и найденные первоисточники (`docs/reports/`, `docs/`, код).
4. Если найден новый устойчивый синтез → предложи или выполни **Save**; если новый отчёт не покрыт в `wiki/index.md` → выполни **Ingest**.

### Lint

Проверка актуальности wiki-страниц.

1. Запусти `python wiki/wiki.py verify` — проверь целостность файлов.
2. Для каждой wiki-страницы проверь:
   - Упомянутые файлы/пути всё ещё существуют.
   - Цифры и выводы соответствуют текущим отчётам.
   - Нет ли новых отчётов, которые дополняют или опровергают синтез.
3. Обнови устаревшие страницы, добавь запись в `wiki/log.md`.

### Generate

Обновление integrity map.

```bash
python wiki/wiki.py generate
```

Запускать после любых изменений в файлах репо. Обновляет `wiki/REPO_integrity.md` с актуальными хешами.

## Формат wiki-страниц

### Research (`wiki/research/`)

```markdown
---
last_updated: YYYY-MM-DD
sources: N
status: active | completed | stale
---

# Название линии исследования

> Одна фраза — что исследовалось и какой главный вывод.

## Хронология

Краткая эволюция: какие этапы, что менялось от этапа к этапу.

## Ключевые результаты

Таблицы, цифры, сравнения — факты из нескольких отчётов.

## Выводы

Что работает, что нет, что стало понятно из совокупности отчётов.

## Открытые вопросы

Что не проверено, где нужно больше данных.

## Источники

- Ссылки на `docs/reports/` с кратким описанием каждого.
```

### Concepts (`wiki/concepts/`)

```markdown
---
last_updated: YYYY-MM-DD
status: confirmed | preliminary | disputed
---

# Название концепта

> Одна фраза — суть концепта.

## Суть

Описание концепта: что это, почему важно.

## Детали

Таблицы, цифры, характеристики.

## Практические следствия

Как это влияет на решения в проекте.

## Где использовано

Ссылки на wiki-страницы и отчёты, где концепт применяется.

## Источники

Ссылки на первоисточники (отчёты, код).
```

## Правила

- Одна страница = одна линия исследования или один концепт. Не смешивать.
- Всегда указывать источники (`docs/reports/`, код).
- Каждая операция = запись в `wiki/log.md`.
- `wiki/index.md` — всегда актуален (обновлять при любом изменении страниц).
- Для `research/`: создавать страницу когда отчёт приносит новое знание.
- Для `concepts/`: создавать когда концепт устойчив и подтверждён данными.
- При обновлении страницы — не переписывать историю, а дополнять хронологию.
